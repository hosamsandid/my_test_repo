About this document

This catalog documents the reusable patterns identified across the mainframe modernization lifecycle — from the first reverse engineering pass over 3M LOC of COBOL/DB2 source, through semantic analysis and knowledge graph construction, to forward engineering and Java code generation. Each pattern captures a recurring, deliberate approach that was applied to solve a specific class of problem in this migration, along with its rationale, trade-offs, and the artifacts it produces.

The catalog is organised by level: the highest level (Modernization Workflow) groups the three main phases; each phase decomposes into specialised sub-levels; and each sub-level contains one or more individual patterns. Reverse Engineering

Reverse Engineering

Patterns applied during the structured analysis of the COBOL/Mainframe source — covering static extraction, semantic enrichment, and knowledge graph construction.

RE-001 Reverse Engineering

Overall Reverse Engineering Process

Functional Overview

The Reverse Engineering phase is the foundational stage of the modernization workflow. Its purpose is to transform an unstructured, ~3 million line COBOL/Mainframe codebase into a suite of structured, machine-readable artifacts that the Forward Engineering phase can consume with confidence. The RE phase is deliberately decomposed into four sequential sub-phases, each building on the previous: (A) Static Analysis, (B) Semantic Analysis, (C) Knowledge Graph Integration, and a final Analysis Readiness Assessment gate.

Each sub-phase produces canonical, versioned JSON artifacts that serve as the single source of truth for downstream phases. A cross-consistency validator checks structural coherence across all artifacts before the handoff to Forward Engineering is signed off. The PHASE-A-HANDOFF.md document is the authoritative navigation surface for downstream consumers, backed by a machine-readable phase-a-handoff.json as the canonical truth.

Technical Implementation

Phase A begins with automated parsing of COBOL source via the Cobolitics tool, supplemented by manual analysis of external C modules (actuarial math bridge and data handler module) that are invisible to the static parser. Phase B enriches structural artifacts with business-language descriptions — use cases, transformation specs per program, and a 2,749-rule business rules catalog. Phase C consolidates all artifacts into a Knowledge Graph using a KDM-inspired ontology with 10 node types and 8 edge types. The Analysis Readiness gate runs a cross-consistency validator across 10 structural invariants; a PASS verdict is required before Forward Engineering may begin.

Strengths & Weaknesses
Strengths
  • Structured phase gating — each sub-phase has explicit acceptance criteria before the next begins
  • Artifact-driven — canonical JSON outputs decouple phases and enable independent tooling
  • Cross-consistency validator provides an objective quality gate before Forward Engineering is unlocked
  • Revision-safe — caveats are documented with fix_type and fix_complexity, not suppressed
Weaknesses
  • Requires deep domain expertise — German insurance terminology must be understood throughout
  • Multiple revision cycles expected; early-phase caveats propagate into downstream artifacts
  • Cobolitics misses dynamic dispatch patterns; supplementary manual analysis cannot be automated
  • Phase B (semantic analysis) is the highest-effort step and resists full automation

Static Analysis

Static Analysis

Automated structural extraction from COBOL source — program inventory, call graph, copybook cross-references, and data division structures.
SA-001 Static Analysis

Cobolitics Static Analysis

Functional Overview

Cobolitics is the static analysis tool purpose-built for COBOL codebases that forms the entry point of the Reverse Engineering phase. In a codebase of approximately 3 million lines, manual inventory creation would be error-prone and prohibitively slow. Cobolitics solves this by automating the extraction of structural metadata from every COBOL source file in a single automated pass, producing the foundational artifact set that all downstream analysis — semantic enrichment, knowledge graph construction, and isolation scoring — builds upon.

The tool is particularly powerful for COBOL because the language has highly structured, parseable syntax for the constructs that drive migration complexity: COPY statements (copybook dependencies), CALL statements (inter-program coupling), EXEC CICS verbs (online interaction surfaces), and DATA DIVISION entries (data structures). These are precisely the facts that determine how hard each program is to migrate — and Cobolitics extracts all of them automatically in a deterministic, schema-versioned JSON format.

Technical Implementation

Cobolitics is invoked per-program and its outputs are merged into slice-level canonical JSON artifacts. It extracts five categories of structural information: (1) Program inventory — name, type (online/batch), CICS interaction classification. (2) Copybook cross-references — all COPY statements with §7-classified relationship types. (3) Call graph edges — all CALL statements with resolution status (static/dynamic/unresolved). (4) Data division structures — all data items with PIC/USAGE clauses, 88-level conditions, and redefine chains (2,424 fields across the slice). (5) CICS command profiles — all EXEC CICS verbs with per-program interaction surfaces.

Known limitation: Cobolitics resolves only static CALL statements. Dynamic dispatch patterns — constant-routing→MOVE→CALL sequences and indirect routing through the data handler module — are not traced and produce unresolved edges in the call graph. These gaps are addressed by the External C Modules Analysis pattern (SA-002) and documented as upstream fix candidates (UF-007 in phase-a-upstream-fix-candidates.json).

Key Steps
1
Run Cobolitics against all in-scope programs
Invoke against 24 COBOL programs and 196 copybooks in the Mainframe slice; collect raw per-program output files.
2
Merge into canonical slice-level artifacts
Aggregate per-program outputs into inventory.json, copybook-xref.json, call-graph.json, data-division-structures.json, and cics-command-profiles.json.
3
Identify unresolved call edges and missing entries
Flag data handler dispatch sites (11 edges unresolved), missing supplement programs (11 inventory entries), and other missing-source callees for Phase A.2 follow-up.
4
Document known limitations as upstream fix candidates
Record indirect dispatch resolution gap as UF-007; catalogue 14 upstream fix candidates (UF-001..014) for future Cobolitics enhancements so they are not silently lost.
Strengths & Weaknesses
Strengths
  • Scales to full codebase size — no manual program-by-program survey required
  • Deterministic and reproducible — same source always produces the same output across revisions
  • Schema-versioned JSON integrates directly with the KG builder, isolation scorer, and other downstream tooling
  • Surfaces unknown dependencies (orphan copybooks, unresolved call edges) that would otherwise remain invisible
Weaknesses
  • Cannot resolve dynamic dispatch patterns (constant-routing→MOVE→CALL, indirect dispatch via the data handler module)
  • 11 data handler dispatch edges and 11 supplement program entries missing from initial pass — require supplementary Phase A.2 analysis
  • Structural output must be enriched with business semantics in Phase B — static parsing alone is insufficient for migration planning

SA-002 Static Analysis

External C Modules Analysis

Functional Overview

The COBOL codebase integrates with two distinct C subsystems that the Cobolitics static parser cannot see: the external actuarial math engine (pure stateless computation, no database access) and the data handler bridge module (routes all DB2 access for 8 COBOL programs). Without explicit analysis of these subsystems, 11 call-graph edges remain unresolved and the data access matrix is incomplete for every data handler caller — making it impossible to correctly model data ownership in the Forward Engineering phase.

This pattern describes the structured two-track approach used to catalog and integrate these hidden C dependencies. It is the direct complement to SA-001: Cobolitics provides the structural baseline, and this analysis fills the gaps that static COBOL parsing structurally cannot cover. The findings feed directly into Pre-Migration Gate isolation scoring, where data handler dispatch edges receive a reduced weight of 0.5 rather than 1.0.

Technical Implementation

Track 1 — Actuarial Math Engine: The primary dispatcher CALCENG1 (63 dispatch entries) and secondary dispatcher CALCENG2 (15 function families) were cataloged via the C bridge source file (calcengine.c). Copybook pairings (actuarial engine→bridge family) were documented, providing the COBOL↔C interface contract. Because actuarial math modules are stateless mathematical functions with no DB2 access, three Java migration paths were identified: JNI wrapping (preserve the binary), Java rewrite (translate the algorithm), or microservice extraction.

Track 2 — Data Handler Bridge Module: The data handler dispatch protocol was reverse-engineered from COBOL caller patterns and the 17 access module bodies in the slice supplement. The protocol: callers populate the handler control structure (DHCTRBLK), set the target access module name and function code (SELECT/INSERT/UPDATE/DELETE), then CALL DHANDLER. Ten dispatch function → DB2 table mappings were cataloged, covering the key tables in the insurance domain. These findings were propagated back into call-graph.json (11 new dynamic_dispatch edges) and data-access-matrix.json (accesses_via_dispatch entries for 8 data handler callers). In the Java target, DHANDLER is replaced entirely by the JPA/Hibernate persistence layer.

Analyse calcengine.c and slice supplement; document CALCENG1 and CALCENG2 dispatch tables (63 + 15 function families); define COBOL↔C copybook pairings; identify Java migration path per actuarial function family.
3
Track 2 — Reverse-engineer data handler dispatch protocol
Analyse COBOL caller patterns; inspect 17 access module bodies; decode the handler control structure (DHCTRBLK); catalogue 10 dispatch function → DB2 table mappings in handler-dispatch-catalog.json.
4
Propagate findings into canonical artifacts
Add 11 dynamic_dispatch edges to call-graph.json; add accesses_via_dispatch entries to data-access-matrix.json for 8 data handler callers; annotate inventory.json with data handler dispatcher metadata.
5
Document residual gaps and Java migration options
Record 2 partially-unresolved data handler callers (PROG195F, ERRHNDLR) as CAV-001; specify Java migration strategy — actuarial engine (JNI/rewrite/microservice) and data handler (fully replaced by JPA/Hibernate persistence layer).
Strengths & Weaknesses
Strengths
  • Fills critical call-graph gaps — 8 programs gain complete, accurate data ownership visibility
  • Enables correct Pre-Migration Gate isolation scoring by weighting data handler dispatch edges at 0.5 rather than a misleading 1.0
  • Documents the Java migration path for both C subsystems before any code is generated
  • Produces self-contained catalogs that decouple future KG updates from re-analysis of the C sources
Weaknesses
  • Requires deep reverse-engineering expertise — no tool support exists for the data handler dispatch protocol
  • The data handler module is binary-only; its full behavior must be inferred entirely from callers and access module bodies
  • 2 data handler callers remain partially unresolved after catalog completion (CAV-001)
  • Catalogs must be maintained manually if caller code or access modules change

Semantic Analysis

Semantic Analysis

Business-language enrichment of structural artifacts — extracting and classifying business rules, defining lifecycle use cases, and producing transformation specifications.
SEM-001 Semantic Analysis

Business Rules Extraction

Functional Overview

The semantic analysis phase transforms the structural artifacts from Phase A into business-language descriptions that capture what the COBOL system does, not just how it is structured. The centerpiece is the extraction and classification of business rules — conditions, validations, calculations, and decision logic embedded in COBOL paragraphs that encode decades of insurance domain knowledge. These rules are the primary correctness contract between the legacy system and its Java replacement: Forward Engineering must implement them faithfully, and the Testing & Validation framework (FE-TEST-001) uses them as the direct specification for rule equivalence tests.

The result is 2,749 individually classified rules, organized into 8 lifecycle use cases and supplemented by 91 decision tables and a quirks catalog. Together these artifacts give every Forward Engineering agent the behavioral specification it needs to generate correct Java code — without requiring access to, or understanding of, the original COBOL source.

Technical Implementation

Rules are extracted through paragraph-by-paragraph analysis of all 24 in-scope COBOL programs and classified by type: validation, calculation, condition, decision, or transformation. At the use-case level, 1,714 rules are absorbed into 8 lifecycle use cases (UC-001 through UC-008). 1,035 rules are cross-cutting — shared logic appearing across multiple use cases that must not be duplicated in the Java implementation.

Decision tables (91 total, 72 absorbed into use cases) provide structured multi-condition representations reviewable by non-technical stakeholders, with 5–7 key rules per use case expressed as business prose. A quirks catalog captures behavioral outliers, non-obvious calculations, and edge cases that could be missed in a linear reading of the COBOL. Twenty-four transformation specifications (one per program) serve as the authoritative blueprint bridging paragraph-level rules to the Java service methods a Forward Engineering agent must produce.

Key Steps
1
Load paragraph inventory from Phase A
Use paragraph-inventory.json as the enumeration of all analysis targets; pair with data-division-structures.json for data field context and 88-level condition names.
2
Extract and classify rules per paragraph
Identify conditions (88-level references), validations (range/type checks), calculations (financial computation formulas), decisions (branch logic), and transformations (data mapping); record in rule-catalog.json.
3
Organize rules into 8 lifecycle use cases
Group rules into UC-001..UC-008; classify 1,714 rules as use-case-specific and 1,035 as cross-cutting; flag rules appearing in more than 3 use cases for shared service deduplication in Java.
4
Build decision tables for branching logic
Produce 91 decision tables (72 absorbed into use cases); each table has condition columns, outcome columns, and business-prose row descriptions that non-technical stakeholders can review and sign off.
5
Catalogue quirks and cross-cutting patterns
Record behavioral outliers and non-obvious calculations in quirks-catalog.json; flag cross-cutting patterns requiring shared Java service implementations rather than per-use-case duplication.
6
Author 24 transformation specifications
Produce one program-level transformation spec per COBOL program; each spec maps paragraphs → rules → Java service methods, giving FE agents a traceable implementation blueprint.
Strengths & Weaknesses
Strengths
  • Creates the definitive behavioral specification that Forward Engineering must implement — no ambiguity about what the system must do
  • Each rule in the catalog becomes a direct test case in the verification phase, creating end-to-end RE→FE traceability
  • Decision tables make complex multi-branch insurance logic reviewable by non-technical stakeholders
  • Quirks catalog prevents domain edge cases from being discovered only in production
Weaknesses
  • Highly labor-intensive — requires domain-expert review of every COBOL paragraph
  • Domain-specific terminology in the customer's business language creates a significant knowledge barrier
  • Rule boundary ambiguity — some business logic spans multiple paragraphs and programs, making scoping judgements necessary
  • Cross-cutting rules require careful deduplication to avoid inflating rule equivalence test counts

Knowledge Graph

Knowledge Graph

Integration of all RE artifacts into a unified, queryable ontology that captures relationships between programs, data structures, business rules, and database tables.
KG-001 Knowledge Graph

Knowledge Graph Creation & Reasoning

Functional Overview

By the end of Phase B, the project has accumulated more than a dozen canonical JSON artifacts covering programs, copybooks, call edges, data structures, business rules, and use cases. These artifacts answer individual questions well but cannot answer relational questions: "which programs must be migrated together because they share a critical copybook?", "which business rules does this DB2 table implement?", "what is the full impact radius of changing this data structure?". The Knowledge Graph is built to answer precisely these questions by integrating all RE artifacts into a single, traversable graph.

The KG is not an optional enrichment — it is the direct input to Pre-Migration Gate isolation scoring (FE-P0-001), the navigation surface for every Forward Engineering Briefing Pack, and the traceability mechanism that allows a FE agent to load only the relevant subgraph for the slice it is implementing. Without the KG, agents would need to manually cross-reference disconnected JSON files; with it, all structural and semantic relationships are explicit and machine-queryable.

Technical Implementation

The KG uses a minimal KDM-inspired (Knowledge Discovery Metamodel) ontology — only the relationships that have proven structurally or semantically significant are included. The ontology defines 10 node types: Program, Copybook, ExternalProgram, Paragraph, DB2Table, DB2Cursor, CICSInteractionPoint, 88LevelCondition, BusinessRule, and BusinessRuleDecision. 8 edge types connect them: calls, depends-on, owns, reads, writes, dispatches_via, implements, and implements_decision. All nodes carry prog:-prefixed IDs for unambiguous cross-artifact reference.

Three companion artifacts are generated: a traceability-matrix.json (program↔rule↔paragraph cross-reference consumed by FE generation agents), a cross-reference-index.json (bidirectional lookup index for fast tooling queries), and an interactive kg-viewer.html for visual exploration. A cross-consistency validator verifies KG coherence against all source artifacts before Phase C is signed off — this check caught a missing node (an actuarial math engine module) that would have silently produced an incorrect isolation score in Pre-Migration Gate had it gone undetected.

1

Specify 10 node types, 8 edge types, cardinality rules, and naming conventions in ontology.md; validate against KDM principles and project-specific constraints before any nodes are populated.
2
Populate nodes
Ingest programs from inventory.json, copybooks from copybook-xref.json, DB2 tables from data-access-matrix.json, paragraphs from paragraph-inventory.json, and rules from rule-catalog.json.
3

Populate calls edges from call-graph.json; depends-on from copybook-xref.json; reads/writes from data-access-matrix.json; dispatches_via from handler-dispatch-catalog.json.
4
Add semantic edges
Populate implements edges (BusinessRule → Paragraph) and implements_decision edges (BusinessRuleDecision → 88LevelCondition) from the rules catalog and transformation specs.
5
Generate companion artifacts
Produce traceability-matrix.json, cross-reference-index.json, and kg-viewer.html; validate that all prog:-prefixed node IDs are consistent across all source artifacts.
6
Run cross-consistency validator and sign off Phase C
Execute the validator (10 structural invariants) against all source artifacts; resolve any incoherence before handoff; a PASS verdict is required to proceed to Forward Engineering Pre-Migration Gate.
Strengths & Weaknesses
Strengths
  • Single navigation surface — any cross-artifact relational query is a graph traversal rather than manual file-by-file searching
  • Powers Pre-Migration Gate isolation scoring directly — call isolation component reads weighted call-degree from KG edges
  • Traceability matrix enables FE agents to load only the relevant KG subgraph per slice, keeping each session focused and bounded
  • Cross-consistency validator catches silent errors (missing nodes, broken edges) that would propagate undetected into scoring and code generation
Weaknesses
  • Expensive to rebuild — any Phase A artifact correction triggers a full KG update cycle
  • Ontology design decisions are hard to change once downstream tools depend on specific node and edge types
  • KG captures structural and rule relationships only — behavioral semantics (execution order, transaction boundaries) are not represented
  • Interactive viewer is read-only; write-back or annotation workflows require separate tooling

Forward Engineering

Forward Engineering

Patterns applied across the migration execution lifecycle — from the pre-phase isolation gate through architecture design, incremental code generation, and validation.

FE-001 Forward Engineering

Overall Forward Engineering Approach

Functional Overview

The Forward Engineering phase takes the complete RE artifact suite as input and produces a running Jakarta EE application. It is structured as a pre-phase (Pre-Migration Gate) followed by three sequential main phases: Phase 1 (domain modeling & roadmap), Phase 2 (architecture design), and Phase 3 (incremental migration execution). This four-stage hierarchy was deliberately designed because the total scope — 30+ output files, 23 tasks, 8 lifecycle slices — far exceeds what any single agent session can safely execute. Each phase is independently reviewable, and a failure or revision in one phase does not invalidate work in unrelated phases.

The most important structural decision is the deferral of per-slice Phase 3 Briefing Packs: they cannot be created until Phase 1A produces migration_slices.json and migration_sequence.json. Without those files, the per-slice dependency chain — which determines which slices must complete before others can start — is undefined. This constraint is explicit in the design and guards against agents starting migration work with incomplete context.

Technical Implementation

The FE phase is executed as a tree of Briefing Packs (BPs). The ROOT BP holds shared context and the overall execution order. Pre-Migration Gate is a standalone leaf BP. Phases 1 and 2 each decompose into two leaf BPs (P1A/P1B and P2A/P2B). Phase 3 is a structural container whose 8 per-slice leaf BPs (SL-001..SL-008) are created after P1A completes — one BP per lifecycle slice, dispatched in the sequence defined by migration_sequence.json. Parent BPs (ROOT, P1, P2, P3) are never dispatched to agents; only leaf BPs are executed. Each leaf BP carries explicit acceptance criteria tied directly to its output files, making completion unambiguous.

8 leaf BPs executed in dependency order. Each covers the full domain/repository/service/controller/mapper/batch/test stack for one lifecycle slice. Read-only slices execute first; transactional slices last.
Strengths & Weaknesses
Strengths
  • Independent phase reviewability — a failure or revision in one phase does not cascade into others
  • Sequential gating ensures each phase receives complete, validated inputs before starting
  • Briefing Pack decomposition matches individual agent session capacity — no single session is overloaded
  • Deferring Phase 3 slice BPs until P1A completes prevents agents from starting migration with an undefined dependency chain
Weaknesses
  • Strictly sequential gate structure — phases 0 → 1A → 1B → 2A → 2B must complete before Phase 3 begins
  • Per-slice Phase 3 BPs cannot be pre-authored; BP creation is blocked on P1A output
  • Total execution spans many agent sessions, requiring careful handoff management between each

Pre-Migration Gate

Pre-Migration Gate — Isolation Score Pre-computation

A mandatory gate before migration sequencing that computes a composite structural isolation score for every program and lifecycle use case, providing the objective foundation for migration ordering decisions.
FE-P0-001 Pre-Migration Gate

Isolation Scores Gate

Functional Overview

Before defining migration slices or sequencing work, an objective, quantitative measure of how structurally isolated each program and use case is must be established. The Isolation Scores Gate computes a composite isolation score for all 24 in-scope programs and 8 lifecycle use cases. These scores become the primary input to the Phase 1A sequencing decision: programs and use cases with high isolation scores are migrated first (lower risk, fewer structural dependencies to coordinate), while deeply embedded programs are migrated last when the surrounding slice boundaries have already been stabilised.

Without this gate, migration sequencing would be based on intuition or business priority alone, with no structural evidence. A business-critical program that is also the most deeply coupled in the codebase would be an obvious candidate for early migration based on priority — but a structural disaster in practice, because it shares data structures with half the slice. The scoring makes this tension visible and quantifiable before any code is written.

Technical Implementation

The composite score is a weighted sum of three independent components, each measuring a different dimension of structural coupling:

Call isolation (40%) — computed as 1 / (1 + weighted_call_degree). Not all call edges count equally: a normal resolved in-slice call has weight 1.0; a data handler dispatch edge has weight 0.5 (the actual target is a data-access function, not a business program); a call to a missing-source program has weight 0.0 (no in-slice coupling to measure). This weighting prevents handler-heavy programs from appearing artificially isolated or artificially coupled.

Shared data isolation (40%) — the sum of copybook fan-in counts across all copybooks the program references. A copybook referenced by many programs is a shared data structure; modifying it requires coordinating all its consumers. Cross-UC isolation (20%) — count of distinct lifecycle use cases in which the program appears, normalized over 8. Programs that appear in many use cases are structural hubs that affect multiple migration slices simultaneously.

Programs tier into three bands: Tier A (≥ 0.60 — well-isolated structural leaves, safe to migrate early), Tier B (0.30–0.59 — moderately coupled, sequence with care), Tier C (< 0.30 — structurally embedded, migrate last). Three use cases with null scores (UC-003, UC-006, UC-007) are hollow — handled by the Java front-end with no COBOL substrate; a null score must not be read as "easy to migrate."

Key Steps
1
Ingest RE canonical artifacts
Load call-graph.json, copybook-xref.json, data-access-matrix.json, and use-case-catalog.json as the four required inputs.
2
Compute weighted call degree per program
For each program, sum edge weights across outbound call-graph edges: resolved in-slice × 1.0, data handler dispatch × 0.5, missing-source × 0.0. Derive call isolation: 1 / (1 + weighted_degree).
3
Compute shared data isolation
For each program, sum the fan-in counts of all copybooks it references (shared-write structures apply a 0.05 penalty per shared-write flag). Higher fan-in = lower isolation.
4
Compute cross-UC isolation
Count distinct lifecycle use cases (UC-001..UC-008) in which each program appears. Normalize over denominator of 8. Programs present in 1 UC score highest; programs present in all 8 score lowest.
5
Compose scores and assign tiers
Composite = 0.4 × call_isolation + 0.4 × data_isolation + 0.2 × crossUC_isolation. Assign Tier A (≥ 0.60), B (0.30–0.59), or C (< 0.30). Flag hollow UCs (null composite) explicitly.
6
Produce readability report and gate Phase 1A
Author isolation-readability-report.md translating scores into plain-language structural observations; run sequencing-gate-report.md coherence checks; Phase 1A may proceed on PASS.
Strengths & Weaknesses
Strengths
  • Objective, data-driven input to sequencing — replaces intuition with structural evidence derived directly from RE artifacts
  • Weighted edge treatment eliminates noise from data handler dispatch and missing-source callees that would otherwise distort scores
  • Tier classification makes results immediately actionable — Phase 1A can read the tiers directly into slice sequencing
  • Hollow use cases are explicitly flagged with null scores, preventing them from being silently misread as trivially simple
Weaknesses
  • Scores capture structural isolation only — a Tier A program can still carry highly complex business rules
  • The 0.5 weight for data handler edges and 0.05 shared-write penalty are calibrated design choices that could be argued differently
  • Three hollow use cases (UC-003, UC-006, UC-007) require a separate migration treatment that the score alone does not prescribe

Architecture

Architecture Design

Target application architecture and binding technology stack — the foundation that constrains and guides every subsequent code generation decision.
FE-ARCH-001 Architecture

Target Architecture & Technology Stack

Functional Overview

Before any Java code is generated, the target architecture and technology stack must be explicitly defined and locked in a binding document. This ensures all Forward Engineering agents produce code that is consistent, directly integrable, and immediately deployable — rather than discovering incompatibilities when 8 independently generated slices are assembled. The choice of JBoss EAP 8 / Jakarta EE 10 is not discretionary: it is mandated by the target production runtime profile, the production environment the migrated application must run in. Every other technology choice flows from this constraint.

The architecture pattern and tech stack choices have a compounding effect: they determine what Java features agents may use, which dependencies they may declare, which annotations are correct, and how layers must be structured. Getting these right before Phase 3 begins eliminates an entire class of post-generation rework — rework that would otherwise require touching every generated slice to align it with a late-decided standard.

Technical Implementation

Architecture decisions (ADRs): ADR-APP-001 selects the modular monolith pattern — a single WAR/EAR deployment, domain-partitioned internally into 4 bounded domains, each with its own controller/service/repository/domain layers. Microservices were explicitly rejected for the PoC: the distributed transaction complexity would exceed the scope and the mainframe's tight ACID guarantees cannot be relaxed. ADR-STRANGLER defines a proxy-based strangler fig approach for gradual live cutover — incoming requests are routed to Java for migrated slices and to legacy COBOL for the rest, with routing managed in proxy_routing_config.yaml.

Technology stack (binding): The tech_stack_manifest.md is the single source of truth for all dependency versions. Key constraints that all agents must honour: Hibernate 5.6 is pinned — JBoss EAP 8.0.6.GA ships this version and upgrading to Hibernate 6.x is prohibited. Jakarta Batch 2.1 / JBeret replaces any batch scheduling, and Spring Batch is explicitly prohibited. ArchUnit rules (archunit_rules.java) enforce the 4-layer architecture at build time: a controller may not reference a repository directly, and a domain class may not reference a service. Any violation fails the build.

Key Technology Choices
●
Runtime — JBoss EAP 8.0.6.GA / Jakarta EE 10 / Java 21 LTS
Mandatory runtime per production runtime profile. Provides CDI 4.0, JAX-RS 3.1, JPA 3.1 (Hibernate 5.6), Jakarta Batch 2.1, Jakarta Security 3.0, Transactions 2.0, and MicroProfile 6.1.
●
ORM — Hibernate 5.6 (PINNED, not 6.x)
JBoss EAP 8 ships Hibernate 5.6; the Hibernate 6.x API must not be used. Replaces the data handler module entirely — all DB2 access is rewritten as JPA entities with Hibernate 5.6 queries.
●
Architecture pattern — Modular Monolith (ADR-APP-001)
Single WAR/EAR, 4 domain modules, 4-layer structure per module (controller / service / repository / domain). ArchUnit rules enforce layer boundaries at build time, failing the build on any violation.
●
Cutover strategy — Strangler Fig Proxy (ADR-STRANGLER)
A proxy layer routes incoming requests to Java (migrated slices) or legacy COBOL (remaining slices) via proxy_routing_config.yaml. Enables live parallel operation and gradual cutover without a big-bang switchover.
○
Prohibited — Spring (all modules), Quarkus, Micrometer standalone
Spring Boot, Spring Batch, Spring Cloud Gateway, Spring Security, Spring Data, Spring WebFlux, Quarkus, and Micrometer standalone are prohibited. All are superseded by Jakarta EE 10 / JBoss EAP 8 equivalents documented in the manifest.
Strengths & Weaknesses
Strengths
  • Binding manifest prevents version drift across 8 independently generated slices — all agents work from the same dependency baseline
  • ADRs capture rationale with explicit trade-off reasoning, making decisions reviewable and challengeable by the client
  • ArchUnit enforcement catches layer violations at build time — structural regressions fail the build before they reach code review
  • Runtime profile compliance is guaranteed from the first generated line of code, not retrofitted at the end
Weaknesses
  • Pinned Hibernate 5.6 forecloses Hibernate 6 query improvements and the new criteria API
  • Prohibition of Spring means maintenance teams need a different knowledge profile than the typical Java market default
  • Modular monolith boundaries are only as good as the domain model — incorrect domain boundaries discovered post-migration would require significant refactoring

Code Generation

Java Code Generation

Migration slice definition and incremental per-slice code generation — how the COBOL codebase is partitioned into independently executable migration units and translated to Jakarta EE Java.
FE-CG-001 Code Generation

Migration Slices & Java Code Generation

Functional Overview

The migration slice pattern is how the monolithic COBOL codebase is partitioned into independently executable migration units. Each slice corresponds to one lifecycle use case (UC-001 through UC-008) and groups the COBOL programs, copybooks, DB2 access patterns, and business rules needed to implement that use case in Java. The slice boundary determines the scope of one agent session's code generation work, ensuring each session has a focused, bounded context rather than a sprawling multi-use-case scope that would exceed any practical agent capacity.

Slices are sequenced using isolation scores from Pre-Migration Gate: high-isolation, read-only slices execute first to establish a stable domain entity foundation; transactional and batch-heavy slices execute last, when the shared data structures they depend on have already been finalised by earlier slices. This sequencing discipline prevents the most common class of cross-slice conflict — two slices independently defining the same JPA entity in incompatible ways.

Technical Implementation

Slices are defined in migration_slices.json (produced by Phase 1A). Each slice entry specifies: the use case it implements, in-scope programs, copybooks, DB2 tables accessed (direct and via data handler dispatch), the predecessor slice in the dependency chain, API contracts (one OpenAPI YAML), and acceptance criteria from the register. Each slice executes as a dedicated leaf Briefing Pack (SL-001..SL-008) with a fixed 10-task template covering the complete vertical stack.

The 4-layer architecture (controller / service / repository / domain) is applied per slice and enforced by the ArchUnit rules from Phase 2B. The data handler module is replaced entirely by the JPA/Hibernate repository layer — no data handler calls appear in the generated Java code. MapStruct handles all DTO ↔ domain object mapping, eliminating hand-coded conversion logic. Where the COBOL slice includes batch programs, Jakarta Batch 2.1 ItemReader/ItemProcessor/ItemWriter jobs replace the Control-M scheduled COBOL. Each slice concludes with a Flyway migration script and a proxy routing update that directs traffic for the now-migrated use case to the Java implementation.

10-Task Slice Execution Template
1
Context review
Load slice_context_{id}.json, the KG subgraph for this slice's programs, transformation specs, and acceptance criteria. Verify predecessor slice is complete before proceeding.
2
Domain entities
Generate JPA entities from target_data_model.sql and type_conversion_decisions.json. Apply Hibernate 5.6 annotations. Reference shared entities from predecessor slices — never redefine them.
3
Repository layer
Implement JPA repositories replacing the data handler dispatch for this slice's DB2 tables. One repository class per aggregate root. Use only Hibernate 5.6 query API — no Hibernate 6 or Spring Data.
4
Service layer
Implement business logic from the transformation specs and rules catalog for this slice. One @ApplicationScoped service per bounded context. Cross-cutting rules reference shared services from earlier slices.
5
Controller layer
Implement JAX-RS resource classes from api_contracts/{slice}.yaml. All endpoints follow /v1/... path versioning. Resource suffix required on all controller classes.
6
Mappers & batch jobs
Generate MapStruct mappers (DTO ↔ domain). Implement Jakarta Batch ItemReader/ItemProcessor/ItemWriter steps to replace any Control-M-scheduled COBOL batch programs in this slice.
7
Database migration & proxy routing
Write Flyway migration scripts for schema changes. Update proxy_routing_{id}.yaml to route this slice's use case endpoints from legacy COBOL to the new Java implementation.
8–10
Tests, parallel-run spec & cutover checklist
Write JUnit 5 + Arquillian tests covering acceptance criteria. Produce parallel_run_spec_{id}.json (inputs and expected outputs for live parallel validation). Complete cutover_checklist_{id}.md.
Strengths & Weaknesses
Strengths
  • Focused scope per session — one use case per BP keeps agent context bounded and acceptance criteria verifiable
  • Dependency-ordered sequencing prevents shared entity conflicts between slices
  • High-isolation slices first creates a stable domain entity layer before complex transactional slices build on top of it
  • Fixed 10-task template ensures every slice covers the full vertical stack — no layer is accidentally omitted
Weaknesses
  • Sequential dependency chain limits early parallelism — slices sharing entities cannot execute concurrently
  • Shared JPA entities defined by the first slice that owns them must be designed for all consumers upfront, requiring global data model awareness in Phase 1B
  • Proxy routing accumulates across 8 slices and must be version-controlled carefully to avoid stale route conflicts during the parallel-run period

Testing & Validation

Testing & Validation

The multi-track verification framework applied to generated Java code — covering structural correctness, business rule equivalence, workflow scenarios, and cross-UC consistency.
FE-TEST-001 Testing & Validation

Testing & Validation Framework

Functional Overview

Migrated Java code must satisfy two fundamentally different correctness criteria: structural correctness (does the code conform to the defined architecture and standards?) and behavioral correctness (does the Java code produce the same business outcomes as the original COBOL?). These are distinct verification dimensions requiring different tools and approaches. Conflating them — or addressing only one — creates dangerous blind spots: code that passes all unit tests but violates layer boundaries, or code that compiles cleanly but produces wrong premium calculations.

The framework is organized into four tracks, each targeting a specific failure mode. Together they form a verification ladder: structural checks run earliest (build time), rule equivalence checks validate individual business behaviors per slice, workflow tests validate multi-slice interaction, and cross-UC consistency checks validate the shared entity layer across the entire migrated application. A defect caught in Track 1 at build time costs orders of magnitude less than one surfaced in Track 4 during cross-UC integration testing.

Technical Implementation

Track 1 — Static verification (build time): ArchUnit rules enforce the 4-layer architecture on every build. Prohibited patterns include: controller → repository direct calls, domain → service references, and Jakarta EE annotation misuse (e.g., @SessionScoped on a service). Build fails on any violation. Coding standards compliance (naming conventions, import restrictions, prohibited Spring annotations) is checked here too. This track has zero false negatives for the patterns it targets — if the rule fires, the code is wrong.

Track 2 — Rule equivalence (per slice): Test cases are derived directly from rule-catalog.json. Each rule entry in the catalog maps to one or more JUnit 5 test methods that exercise the Java implementation with the same input conditions the COBOL logic would receive. This creates end-to-end RE→FE traceability: every catalogued rule has a corresponding test, and a test failure is immediately traceable to the specific rule that broke. Tests run via Arquillian against a deployed EAP instance to exercise the full persistence stack.

Track 3 — Workflow scenarios: Cross-slice end-to-end tests exercise complete lifecycle workflows — initiation → financial processing → settlement → amendment — catching integration regressions that pass individual slice tests but fail when slices interact. These tests consume the parallel_run_spec_{id}.json files produced during slice generation, which define the expected outputs for known business scenarios.

Track 4 — Cross-UC consistency: Validates that shared JPA entities (mapped from shared copybooks) produce consistent behavior across all use cases that reference them. A shared entity modified by one slice's service method must not break another slice's invariants. This track specifically targets the failure mode that sequential slice migration creates: entity schema decisions made in slice N can silently break assumptions in slice N+5.

The Four Verification Tracks
1
Static — ArchUnit & build validity (every build)
Layer isolation, naming conventions, prohibited imports, annotation misuse. Runs on every Maven build. A violation is a build failure — no code review needed for this class of defect. Defined in archunit_rules.java from Phase 2B.
2
Rule equivalence — per-slice behavioral tests
One JUnit 5 test method per rule in rule-catalog.json for the slice. Covers validations, calculations, condition branches, and decision table rows. Runs via Arquillian against a running EAP instance. Direct RE→FE traceability: rule ID in test name maps back to catalog.
3
Workflow scenarios — cross-slice lifecycle tests
End-to-end lifecycle flows (initiation → financial processing → settlement, etc.) exercised across multiple migrated slices. Detects inter-slice integration regressions. Inputs and expected outputs sourced from parallel_run_spec files. Run against the full deployed application.
4
Cross-UC consistency — shared entity validation
Validates that shared JPA entities produce consistent business results across all use cases that reference them. Catches cases where a slice's service logic modifies a shared entity in a way that violates the invariants of a different use case.
Strengths & Weaknesses
Strengths
  • ArchUnit catches structural drift at build time — the cheapest possible moment to detect and fix it
  • Rule-catalog-derived tests create direct, auditable traceability from RE artifacts to FE verification — no rule is untested by construction
  • Four-track structure means any failure has a known category, making root-cause diagnosis significantly faster
  • Workflow tests catch the class of regression that slice-level unit tests are structurally unable to detect
Weaknesses
  • Rule equivalence tests require COBOL baseline test data — if no historical test data exists for the slice, it must be synthesised from the transformation specs
  • Date-dependent calculations (financial accrual, payment schedules) require stable test-clock setup to be deterministic
  • Arquillian tests require a running EAP instance in CI, adding infrastructure overhead compared to plain JUnit tests
  • Cross-UC consistency tests must be actively maintained as slice boundaries are refined post-migration; stale tests can give false confidence
