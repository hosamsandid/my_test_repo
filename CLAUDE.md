# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

> High-level map. Deep specs live under `docs/`; ticket-level history lives in git.

## Project Overview

**agent-studio** is a local Matrix-to-Claude-Code stack for an enterprise context. It provides chat-based AI agents extensible with domain-specific skills for **Mainframe Migration** (COBOL, JCL, DB2, IMS, etc.).

The stack runs locally with Podman as a single compose file: **Conduwuit** (Matrix homeserver); **Orchestrator** (control-plane, spawns/manages one container per agent, no Matrix identity); **Admin Console** (web UI on `:4000` for agents, environments, SSH keys, skills, etc.; embeds a chat UI at `/chats/:agentId`); **bp-explorer** (read-only viewer for ACE BriefingPack metadata).

The LLM backend is reached via an Anthropic-compatible proxy: `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` in `.env` (gitignored). Default Sonnet/Haiku models set there too.

**Model Provider auth types.** A registered Model Provider (`/workspace/llm-endpoints/index.json`, tokens in `_keys/` at 0600) carries an `authType`: default **`api-key`** (Bearer against `baseUrl`) or **`oauth-token`** (Claude *subscription* auth via `claude setup-token`). For `oauth-token` the orchestrator injects `CLAUDE_CODE_OAUTH_TOKEN` and strips `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_API_KEY` so the CLI talks directly to `api.anthropic.com`. The login flow runs server-side under a PTY (`orchestrator/llm-auth-flow.js`, `/api/llm-auth/flows/*`); the token is claimed server-side, never reaching the browser. **Compliance:** consumer-subscription OAuth tokens are single-user only (Anthropic Consumer Terms) — creating/re-keying one requires a single-user confirmation recorded as `complianceAck`. One-shot server-side generation (`resolveAssistTarget`) skips `oauth-token` providers.

## Architecture

All human↔agent communication happens through **direct messages**: each agent has its own Matrix user; the human chats with it in a dedicated 1:1 room. There is no shared multi-agent room and no central routing identity.

```
Admin Console chat UI (or any Matrix client) → Conduwuit (localhost:8448)
       └── 1:1 DM rooms (one per agent, e.g. @cobol-agent:local ← as-agent:latest)

orchestrator.js (control-plane container, no Matrix presence)
  ├── Manages agent lifecycle (create/update/delete via Admin Console)
  ├── Spawns ONE Podman container per enabled agent over the libpod
  │     socket (/var/run/podman.sock) via spawn-container.js
  ├── Provisions per-agent network + volume isolation; reconciles live
  │     containers (by the `aee.agent.id` label) against its map
  ├── Provisions new agent Matrix users via the admin client
  └── Internal HTTP API on :4002 for the admin console
```

- **Agents** are dynamically created Matrix users, each in its **own** Podman container (`as-agent:latest`), lifecycle-managed by the orchestrator. Configs persist in `/workspace/agents/<id>/` (`config.json` + `CLAUDE.md` + `AGENT-PROMPT.md`); DM room id in `dm-room.json` (created lazily by the console).
- Each agent is bound to a **Working Environment** (below) defining what gets seeded into its workspace.
- **Container-per-agent isolation** is three-way: per-agent **network**, per-agent **filesystem** via a SubPath mount of the pool volume (`AEE_WORKSPACE_ISOLATION`, default on), optional **dedicated volume** (`AEE_PER_AGENT_VOLUME`, opt-in). Optionally a fourth: an admin can bind-mount one or more **host folders** inside the container (podman/local only — see `docs/context-mount.md`), **read-only by default** or **read-write** per folder. A single legacy folder mounts at `/context` (`contextMount` + optional `contextMountRw` in `config.json`); multiple folders (#1290) persist as `contextMounts: [{ path, name, slug, readWrite? }]`, each at a distinct `/context/<slug>` target (`resolveContextMounts` reconciles either shape). The mounts exist **only in the agent's container**, so the console browses each *through* that container (#1286) and the agent is told about them by a gated CLAUDE.md section.
- **Agent runtime**: the container entrypoint `agent-image/scripts/agent-entrypoint.py` (+ `sase_lib.py`) — Matrix client + Claude CLI invocations + trigger scheduler.

### Teams (human collaboration & visibility scope)

A **Team** (the *human* grouping) is the tenant/scope resources and human users are assigned to. **Do not confuse it with the `role: "team"` agent construct**, always called an **Agent Team** (an agent squad working a repo); they only share a word. Data model: three JSON collections under `/workspace` (`teams/`, `users/`, `memberships/index.json`); roles: **System Admin** (global, `user.systemAdmin`), **Team Admin**, **Team Member** (per-team). Every agent construct, env, and credential carries a `teamId` (default `default`). **Exception — personal credentials (#1567/epic #1558, Phase 1):** the new `personal` ownership tier carries a `userId` (the owner) and `teamId: null`; it is not team-owned.

Source of truth: `orchestrator/teams-store.js` (pure factory). The orchestrator bootstraps the default team + an optional System Admin (`BOOTSTRAP_SYSTEM_ADMIN_SUBJECT`) and backfills `teamId` at startup. CRUD at `/internal/admin/{teams,users,memberships}` (proxied `/api/admin/...`) — **distinct** from `/internal/teams/*` and `POST /api/teams`, which manage Agent Teams. Driven by the **Access & Users** page (`/teams`, `Teams.jsx` — the nav label was renamed from "Teams" in #1726 to avoid confusion with the *Agent Team* construct; route/API/internal entity stay `team`).

**Resource scoping.** List endpoints are filtered by the caller's team membership via `admin-console/api/scope.js`. The env admin + any System Admin get full visibility (`all: true`); others see only resources whose `teamId` is one of their memberships (global/pool skills always visible). **Exception — personal credentials (#1567):** the personal tier is checked *before* `scope.all`; only the credential's owner (by `userId`) can see or manage it — not a System Admin, not the env single-admin. Full spec: `docs/teams-data-model.md`.

### Working Environments

A **Working Environment** is a reusable **infrastructure template** at `/workspace/environments/<envId>/environment.json`: `id`/`name`/`description`; `repositories` (array of `{url, branch, sshKeyId, readOnly}`, zero or more repos cloned at creation — `[]` is valid for LLM-only / credential-free agents; `readOnly` (#1813, default off) still clones the repo but annotates it *reference-only — do not commit or push* where it is listed in the agent's generated context, changing awareness not availability; legacy single `repository` is migrated to a one-element array on read by the API, ~api.js line 695); `mcpServers` (optional `{serverId, credentialId}` refs into the MCP registry); `additionalContext` (optional text appended to CLAUDE.md).

**Environments do NOT carry skills — never re-add them.** The skill *grant* is **team-owned** (`orchestrator/skill-grants.js`): team agents (`role: team`) carry `skills[]` (inherited by every member without a `skillsOverride`); standalone agents/orchestrators carry their own; bp-instances inherit from their parent orchestrator. `effectiveSkills(cfg, loadCfg)` resolves the grant everywhere (seeding, CLAUDE.md gating, preview).

**Skill seeding & activation.** Every seed writes a per-agent manifest `/workspace/agents/<id>/.agent-studio/seeded-skills.json` (`{name: {tier, seededAt}}`) — the truth for whether a running member actually has a skill. One-click (de)activation is an **additive file sync, not a respawn** (skills are static files read per invocation): `POST /internal/teams/:teamId/skills/{activate,deactivate}` (or `/internal/agents/:id/skills/...`) edits the list + copies/removes per-member files via `planSkillSync`, rebuilds each CLAUDE.md, mirrors into isolated volumes (proxied `POST /api/knowledge/{activate,deactivate}`). At **autonomy level 3** the curator's auto-promotions are auto-activated (learn → bundle → promote → activate, no human).

**Agent creation seeding** (orchestrator): seed `.claude/` + `memory/` from the skill-pool volume (or bundled defaults); copy the resolved skill grant (team-first, then global); patch absolute `/workspace/` paths in memory; materialize the env's MCP refs into the agent's `.claude/settings.json` (per-agent credential substitution); `git clone` if the env has a repo (SSH URLs → `GIT_SSH_COMMAND`; HTTPS GitHub → PAT via `GIT_CONFIG_*`); build CLAUDE.md via the prompt-assembly pipeline.

**Syncing repos into existing agents (#1342).** Repos are cloned at creation only, so a repo added to an environment afterwards never reaches its existing agents. The **Sync repositories** action clones the *missing* repos into an existing workspace without a respawn (the workspace volume is shared with the running container): per-agent on the Agent edit panel (`POST /api/agents/:id/sync-repositories`), or fanned out to every agent on an environment via **Sync all agents** on the Working Environment form (`POST /api/environments/:id/sync-agents`); both stream one NDJSON line per repo per agent and reuse creation-time clone + credential resolution. Idempotent — already-cloned repos are left untouched (no re-clone, fetch, or branch switch). Pure decision logic in `orchestrator/repo-sync.js` (`syncAgentRepoPlan`); the console-side view helpers/stream reader in `admin-console/src/pages/sync-repos-view.js`.

#### System-prompt assembly

The seeded `CLAUDE.md` and a runtime `--append-system-prompt` memory hint are composed by one pure, unit-tested module — **`orchestrator/prompt-assembly.js`** — used by the seed path (`buildAgentClaudeMd`).

- **Ordering.** The authored **Agent Role is hoisted to the top** (after a short identity preamble), ahead of generic blocks (Working Environment → Workspace → Response Formatting → Memory System → Skills → GitHub Actions → Trigger management → Important Notes). Base template read from `/template-workspace/CLAUDE.md` (else `/defaults/CLAUDE.md`), split by H2, re-ordered in code.
- **Conditional gating.** Git/`gh-as-agent` only when the env has a repo; Trigger-management + unattended framing only for **autonomous** agents (`agentIsAutonomous()`: `sessionPolicy: per-invocation`, `orchestrator`/`bp-instance`, or already has triggers); Skills only when the grant is non-empty; the **Context Folder(s)** block (the single-folder *Read-only Context Folder* / *Host Context Folder* wording — #1289 — for a lone `/context` folder, or an enumerated **Context Folders** list for a multi-folder set — #1290) only when the agent carries at least one mount (#1286) — setting or clearing the mounts rebuilds + reseeds CLAUDE.md through `POST /internal/agents/:id/prompt-rebuild` before the respawn, so the prompt never advertises a folder the container lacks. Adding/removing a trigger via the Flow Editor (`PUT/POST/DELETE /api/agents/:id/triggers`) that flips `agentIsAutonomous()` rebuilds + reseeds CLAUDE.md immediately (#962, `reconcileAgentAutonomyPrompt`); a no-op edit that doesn't change the autonomy state never rebuilds.
- **Runtime hint.** `buildMemoryHint(blueprintId)` is **byte-identical** to `_build_memory_hint()` in `agent-entrypoint.py` (test-asserted; change both in one commit).

SSH keys are stored at `/workspace/environments/_keys/<keyId>` (mode 0600), metadata in `_keys/index.json`. The private key is **never** returned by the API — only its fingerprint.

#### Why both an SSH key and a GitHub PAT? (defense-in-depth)

Not redundant. SSH key → git I/O on SSH URLs (via `GIT_SSH_COMMAND`); can be a per-repo read-only deploy key. GitHub PAT → git I/O on HTTPS GitHub URLs, Events API polling, and `gh pr create`/commit/review (`gh-as-agent`, via `GH_TOKEN`/`GITHUB_TOKEN`). **Blast-radius separation:** a leaked SSH key can't merge PRs; a leaked PAT didn't grant the initial clone. For HTTPS-only repos the PAT covers both — prefer SSH URLs + deploy keys.

**Credential rotation propagates to running agents.** Spawn-time credentials (PAT from `env.githubTokenId`, per-agent SSH identity) are baked into each container at `startAgentProcess`, immutable for its lifetime. Repointing an env at a different token → `PUT /api/environments/:id` detects the `githubTokenId` change and best-effort calls `POST /internal/environments/:id/respawn-agents`, recreating every running agent bound to that env. Disabled agents pick up the fresh credential on next enable. **Personal-credential rotation** is a distinct mechanism: `POST /api/{ssh-keys,github-tokens}/:id/rotate` replaces the stored secret in place (keeping id/name/owner), and is personal-tier only and owner-gated — a team/system credential is refused (`rotate-personal-only`). **Rotation now propagates to running agents (#1570, Phase 4):** setting *or* rotating a personal SSH key / GitHub token best-effort calls `notifyOwnerCredentialChange(userId)` → `POST /internal/owners/:ownerId/respawn-agents` → `respawnAgentsForOwner`, the owner-scoped sibling of `respawnAgentsForEnvironment` — it respawns only *that human's* running agents (matched by `credential-resolution.selectAgentIdsForOwner`/`resolveAgentOwnerId`, so a team-member is matched via its parent team's owner), leaving other humans' agents and unrelated environments untouched, and skipping disabled/not-running/tokenless agents like the env path. This also closes the prior gap where an SSH-key change triggered no respawn at all. Because the respawn interrupts in-flight work, the My Credentials rotate panel warns the owner to rotate at a quiet moment. **Offboarding (#1571, Phase 5):** deactivating a human (`DELETE /internal/admin/users/:id`) now calls `orchestrator.offboardOwner(userId)` before `teamsStore.deleteUser` — it **pauses** (drains, never wipes) the departed person's agents (same `selectAgentIdsForOwner` owner match) and **auto-deletes** their personal SSH keys + GitHub tokens (index entries + 0600 secret files, via `credential-resolution.selectPersonalCredentialIds` — team/system credentials are never touched, AC3); pausing first means an in-flight attributed write that outlives the pause refuses rather than acting under a now-deleted identity, and there is deliberately no admin break-glass into the secrets before deletion (D6/D2).

**My Credentials (self-service, #1568 Phase 2).** Every authenticated human — not just a credential admin — manages their own personal SSH key and GitHub token from the **My Credentials** page (`/my-credentials`, no `credAdmin` gate). The page shows only the caller's own personal entries (re-asserted by `personalCredentials(list, myId)` in `admin-console/src/pages/my-credentials-view.js`, which re-checks `userId === me` even though the API already caller-scopes the list). Operations: **create** (paste or server-generate for SSH; paste for token; owner always forced to caller server-side via `resolveCredentialOwnership`), **list** (metadata/fingerprint only; raw secrets never returned after creation), **rename**, **rotate in place** (personal-tier only — see above), **delete**. The env single-admin (no user record, `userId: null`) cannot own personal credentials (`canOwnPersonalCredentials` fails closed) and sees an explanatory note instead of an empty page. The admin **SSH Keys** / **GitHub Tokens** pages filter personal credentials out of their tables via `adminManagedCredentials` (also in `my-credentials-view.js`), so the two tiers remain visually and navigationally distinct. `credential-scope-view.js` gains an `isPersonalCredential` helper and a `userId`-aware `canManageCredentialClient` that checks `userId === owner` before the `isSysAdmin` shortcut (mirrors `scope.js`).

**Personal-credential runtime resolution (#1569, Phase 3).** The pure, unit-tested decision core lives in `orchestrator/credential-resolution.js` (`resolveAgentOwnerId` / `findPersonalCredential` / `resolveCredential` / `ATTRIBUTED_OPERATIONS`). The rule is **per operation class**: **attributed writes** (commits, pull requests, reviews, HTTPS pushes — `ATTRIBUTED_OPERATIONS`) carry the human's name and prefer the owner's personal token (personal → team → system order); read-only clones, the repo-check probe, and event polling are shared-eligible and may use a team/system credential. **Refuse-on-missing (AC5):** when an attributed write's owner has no usable personal credential, the run **refuses** with a clear HTTP 424 `personal-credential-required` error — it does not silently drop to a shared identity. **`ownerId`-presence is the switch (AC8 reconciliation):** an agent with no `ownerId` — every agent today, since nothing populates it yet — takes the shared token exactly as before and is never refused; only an agent carrying an `ownerId` is subject to the personal preference + refuse-on-missing. The orchestrator wires the decision into `agentCreatePr` via `resolveAttributedGithubToken` (reads `config.ownerId` from persisted config, never the trigger initiator — AC3), which wraps the pure core with the credential-index read (`index.json` metadata only — raw secrets never loaded) and surfaces refusal as the distinct 424 error. The `_buildAgentGitEnv` signature gains an `overrides` param so the resolved personal token id (or the shared one) is threaded cleanly without altering unrelated paths.

### MCP Servers

Static skills live in the workspace; **MCP servers** are how agents reach runtime data (wikis, vector stores, graph DBs). The pattern mirrors the SSH/PAT split: a *catalog* of servers, a *separate* credential store, an environment that pairs them.

- `mcp-servers/<id>/server.js` (repo) — reference implementations baked into the image; `make seed-mcp-servers` lays them into `/template-workspace/mcp-servers/<id>/`. The shipped `wiki/` server is a single-file stdio MCP over a REST backend.
- `/workspace/mcp-servers/<id>/server.json` — operator-managed **registry**: `id, name, description, transport (stdio|http|sse)`, plus stdio `command, args, env` or http/sse `url, headers`. `env`/`headers` support `${credential}`, substituted per-agent at seed time.
- `/workspace/mcp-credentials/_keys/<credId>` — raw secret (0600, never returned); `index.json` holds metadata. Credentials are global (one token can back two environments).

**Per-agent isolation.** At seed time the orchestrator reads `env.mcpServers` (or a member's `mcpServersOverride`), substitutes `${credential}`, and writes the merged stanza into **the agent's own** `.claude/settings.json` under `mcpServers[<serverId>]` (Claude Code schema: stdio `{command, args, env}`; http/sse `{type, url, headers}`). No pool-wide MCP config. `mcpServersOverride` on a member replaces the env's MCP set for that member; absent = inherit.

### Plugins (governed capability extensions, #1516)

Agents reach the outside world (container runtimes, test-management systems, …) **only** through registered **platform plugins** (not to be confused with Claude Code "agent plugins"). A plugin pairs a privilege-holding **broker sidecar** with a dependency-free **CLI facade** seeded into the agent workspace — CLI-first (deliberately not MCP), all security server-side, "one contract, two provenances" (`docs/cli-contract.md`). Concept: `docs/plugin-system-concept.md`. Built in phases (#1517 core machinery → #1522); PR #1287's `podman-mcp` broker becomes plugin #1 in Phase 3.

**Phase 1 core machinery (#1517) — pure, unit-tested modules:**
- `admin-console/api/plugin-manifest.js` — validator/normalizer for a `pluginVersion: 1` manifest (the `process-template.js` discipline). `sidecar.capabilities` is a **closed enum** (`podman-socket`, `egress`, `host-mount:<path>` — a plugin cannot request an arbitrary mount); `scopes` declares the granularities the broker honours (`["team"]` or `["team","agent"]`, must include `team`) and bounds a grant's choice (`assertGranularityGrantable`); optional `defaultScopeGranularity` (within `scopes`) is the **per-manifest** grant default (`defaultGranularity()` → the field, else `team`; the §10 decision, #1519); optional `quota: { maxObjects, ttlSeconds? }` is the **per-scope** resource cap (§4.6); `ui.routes[].minRole` is **validated + reserved** in Phase 1, the proxy/role enforcement lands in Phase 5.
- `orchestrator/plugin-scope-token.js` — generalises `podman-token.js` to HMAC-signed `{pluginId, scopeId}` tokens (broker verifies on every call).
- `orchestrator/plugin-scope.js` — `resolveScopeId(agentCfg, granularity)` (**both granularities from the start**: `team` = team for members / self for standalone; `agent` = the member's own id) + ownership-label helpers (`aee.plugin.owner=<scopeId>` stamp/filter). Granularity multiplies *tokens*, never backend credentials; teardown keys on `scopeId` so deleting one member at `agent` granularity leaves siblings untouched.
- `orchestrator/plugin-sidecar.js` — pure lifecycle planners: `reconcileSidecars` (start installed / stop orphaned sidecars — `aee.plugin.id` label), `reconcileAttachments` (grant-driven per-agent network connect/disconnect — reachability matches grant truth), `capabilityAttachments` (closed-enum → concrete attachments). The impure libpod calls wrap these in the orchestrator runtime.

**Phase 3 — plugin #1 (#1519): the podman sandbox.** `plugins/podman-sandbox/` reworks PR #1287's `podman-mcp` broker onto the plugin machinery: manifest (`podman-socket` capability, `scopes: ["team","agent"]`, `defaultScopeGranularity: "agent"` — the §10 decision, since a sandbox reads as per-agent — and a per-scope `quota` replacing #1287's global container cap) + the dependency-free `aee-podman` CLI facade (`aee-podman run <image>` — single container, no compose file needed; `aee-podman compose up -f compose.yml` — multi-service stack; both route through `compose_up` so `run` is pure CLI sugar with no new broker tool, inheriting validation / isolation / quota identically; contract §4.5, driven by `orchestrator/plugin-cli-contract.test.js`). The broker sidecar source lives at `podman-mcp/` (kept nearly unchanged from #1287; its `owner-scope.js` stamps `aee.mcp-owner=<scopeId>` on every container so scopes can't see each other's). No podman-specific code sits in orchestrator seeding / prompt-assembly.js / Platform Settings (#1287 never merged there). The live-stack remainder (broker verifying the plugin scope-token + enforcing the manifest quota, orchestrator sidecar lifecycle + socket mount + token mint) is the Phase-3 completion step — same "pure core now, live stack next" split as Phases 1–2.

**Phase 4 — Broker SDK (#1520): `broker-sdk/`.** The obligations every broker owes (§4.6/§4.9), packaged as one dependency-free Node module a broker sidecar imports so each plugin author doesn't re-implement — and re-break — them: `verifyScopeToken(reqOrHeader, secret)` → `{pluginId, scopeId}` (**granularity-agnostic** — the broker never learns whether a `scopeId` is a team or a single agent, and must not branch on it; byte-identical contract to `orchestrator/plugin-scope-token.js`), `scopeFilter(scopeId)` (ownership-label stamp/filter/exact-match on the platform label `aee.plugin.owner`), `auditWriter(dir, {retentionMs})` (JSONL-per-call fs writer over the pure `plugin-audit.js` core), `maskSecrets(output, secrets)` (response redaction — explicit secrets + the `-e/--env KEY=VALUE` pass), `healthEndpoint()` / `teardownScopeEndpoint(reap, {secret})` (the two plain-REST routes the orchestrator calls on every broker; teardown is per `scopeId`, so **one** handler serves both team deletion and single-member deletion, and **resources are reaped before the orchestrator invalidates the token**), and `parkForApproval(op)` / `approvalHoldingPen({requiresApproval})` (the `requiresApproval` holding pen, v1 DM-confirm). **Extracted from plugin #1's broker, not designed on paper** — the retrofit repoints `podman-mcp/server.js` at the SDK and **deletes its own `podman-token.js` / `owner-scope.js` / `mask-env.js` copies**; two generalisations ride along (the 3-field platform scope token, and the platform owner label `aee.plugin.owner` in place of `aee.mcp-owner`), container-isolation behaviour otherwise unchanged. SDK use is **recommended, not enforced** — the platform verifies the wire contract, not the implementation. The broker's Docker build context vendors `broker-sdk/` into the image (its context is the repo root). Pure-module discipline, `node --test` covered (forgery, cross-scope isolation at both granularities, secret echo, teardown ordering).

**Phase 5 — plugin #2 (#1521): test management, on the SDK.** `plugins/test-mgmt/` + broker `plugins/test-mgmt/broker/` — a governed test-management capability (Xray/Zephyr/qTest) proving a credential-backed broker is thin: the broker `require`s `../../../broker-sdk` and adds only the credential-holding `vendor-client.js` (the one vendor token lives here, never reaching the agent — why it is a plugin, not a skill) + `broker-policy.js`. The dependency-free `aee-test` CLI facade drives it (`aee-test create-case …`, `aee-test trigger --plan REGRESSION --wait` submit→poll; contract §4.5, in `plugin-cli-contract.test.js`). Three firsts: (1) **authorisation by granularity** — the new manifest `policy` field (`admin-console/api/plugin-manifest.js`) declares per-subcommand rules keyed on the calling scope, enforced by the SDK `authorizeAction`/`isActionPermitted` (`broker-sdk/authz.js`) — `create-case: { scopes: ["agent"], requiresFlowFinal: true }` means only the flow-final agent whose cross-checks passed may create test cases; a team-scoped token cannot express that. (2) the first real **`requiresApproval`** flow — destructive `data-delete` is parked in the SDK approval pen for DM confirm. (3) the **UI-extension surface** decidable core (`admin-console/api/plugin-ui-proxy.js`): `deriveScopeList` (scope discovery derived from the resolved grant — a plugin enumerates only scopes it was granted to), `enforceUiRoute` (`ui.routes[].minRole` refusal), `signViewerHeaders`/`verifyViewerHeaders` (signed viewer identity + effective role) — reserved + unit-tested at this phase; the live iframe proxy/nav were later wired by the Network Plan epic's Phase 2 (#1562, `admin-console/api/plugin-ui-viewer.js`). The orchestrator live-stack (token mint, scope-registry push to the broker, sidecar lifecycle, DM approval round-trip) is the Phase-5 completion step — same "pure core now, live stack next" split as Phases 1–3.

**Network Plan epic (#1554), Phase 3 — plugin #3 (#1563): netzplan, the planning board.** `plugins/netzplan/` + broker `plugins/netzplan/broker/` — the first **UI-bearing** plugin and the first **privilege-less** plugin (`capabilities: []`, `credentials: []`). Manifest: `scopes: ["team"]` (one board per team), `platforms: ["podman","kubernetes"]`, `ui.routes` `/` @ `team-member` + `/admin` @ `team-admin`, `quota.maxObjects`, `cli: aee-plan`. The dependency-free `aee-plan` CLI drives it with a three-rung autonomy ladder: `show` (autonomy 0 — read-only, always allowed) · `tick <milestoneId>` (≥1) · `edit '<op-json>'` (≥2); the broker re-enforces the level authoritatively and `aee-plan` refuses early from a cached `show`. ### Agent Roles

- `agent` — standalone. Responds to DMs in its 1:1 room; with cron/GitHub triggers it can run autonomously.
- `team` — a reusable system-prompt template + shared Working Environment; hosts no agent itself. **Add Member** (or the wizard) spawns `team-member` agents.
- `team-member` — spawned from a team. Inherits the team's `systemPromptTemplate`, the team agent's `skills[]`, and the env's `mcpServers`; records `parentTeamId`. May override `skillsOverride` / `mcpServersOverride` — absence = inherit. **System-prompt mode (#1511)** has three states (`orchestrator/prompt-modes.js` ⇄ byte-identical `admin-console/api/prompt-modes.js`, browser copy `admin-console/src/pages/prompt-mode-view.js`; `resolvePromptMode`/`composeMemberPrompt`): **Inherit from team** (template only); **Additional input** (the team template followed by the member's own text in a delimited `## Agent-specific instructions` section — stored as the addition alone in `config.systemPrompt` + `promptMode: "additional"`); **Exclusive overriding input** (the renamed "Custom" — the member's own text fully replaces the template, legacy config shape kept so existing custom members are byte-identical). Editing the team's `systemPromptTemplate` eagerly rewrites every inheriting **and** every additional member (the latter re-composed team + addition, `updateTeamPrompt`); an exclusive member is untouched. Skill/MCP changes apply at the next member rebuild.
- `orchestrator` — bound to a BriefingPack dir (`briefingsPath`). On creation and each ~30s claim tick it pulls main (60s-throttled), scans the dir, writes one stub `bp-instance` per BP. On a BP → `status: dispatched` it DMs a suggestion; on user confirmation it `curl`s `/internal/agents/:id/claim` (patches `brief.md`, commits+pushes, materialises the bp-instance). Manual Activate / Reset to stub bypasses the suggest flow.
- `bp-instance` — one per Briefing Pack under an orchestrator. A stub (no Matrix user, no workspace) until claimed/activated; bound to one BP, uses the ACE engineering skill to execute its LoopScript.

> **Legacy roles.** `expert`/`expert-group`/`expert-instance` → `agent`/`team`/`team-member` (and `parentGroupId` → `parentTeamId`) on startup and on read.

### Autonomous Agent Triggers

Triggers live in a per-agent `/workspace/agents/<id>/triggers.json`; the scheduler syncs every 60s (`node-cron`). **Self-managed** (the agent can edit its own), **file-based sync**, **per-trigger overlap protection** (a still-running trigger skips the next tick), and **agent-wide serialization** (#1157): an agent has one workspace, so at most one workspace-touching run — a loop iteration, any trigger, or a chat/DM turn — executes at a time. All three paths pass through one `WorkspaceGate` (`agent-entrypoint.py`); while a loop runs it holds the workspace across **all** its iterations and every other trigger and chat message queues (FIFO) until the whole loop ends (completion or user Stop). The pending-drain pauses while a loop is active so `http`/`github-event` work stays durably queued; chat backlog is bounded (`AEE_MAX_QUEUED_CHAT`, default 8); Stop stays out-of-band.

- `cron` (`cron`, 5-field) — recurring. `once` (`at`, ISO) — one-shot, auto-removed after execution.
- `http` (`secret`, auto-gen) — fired by external HTTP POST (see Webhook Server).
- `github-event` (`repo` `owner/name`, `events` e.g. `pull_request.opened`, optional exact-match `labelFilter`, optional `claim: {remove, add}`) — fired by the GitHub poller. **No source/origin filtering** — fires on any matching event regardless of cause. Agent gets the `prompt` + full event payload as JSON. **`claim` field (#957/#958):** when set, the runner mechanically swaps the wake label for a claim label (`remove` → `add`, e.g. `"ready"` → `"ready:wip"`) after the preCheck gate and before the Claude invoke — making work-in-progress visible on GitHub. On a **successful** completion the claim is swapped forward `<wake>:wip` → `<wake>:completed` (#1163), so a finished run stops looking in-progress — the three states (`ready` / `ready:wip` / `ready:completed`) stay visibly distinct. On final double-failure the swap is instead rolled back (`add` → `remove`), which re-emits a fresh `issues.labeled` event and restarts the chain automatically; a user-aborted run keeps its `:wip` (no completed swap, no rollback). A claim label missing in the repo (`gh` doesn't auto-create labels) is created on the fly and the swap retried once (the `:completed` label auto-creates green, distinct from the `:wip` amber). Best-effort — a failed swap is logged and never gates the run. **Convention enforced:** `add` must equal `<labelFilter>:wip` (the bundle validator rejects anything else so Layer-3 reconciliation can always derive the claim label). Channel-derived label listeners get their claim auto-stamped by `expandGithubChannels`; set `autoClaim: false` on the channel port to opt out. **`transport: 'internal'` (#1173):** the listener is excluded from the poller plan (`pollerSubscribes`) and woken directly by `POST /internal/flow-emit` (producer CLI `aee-emit`) — enqueue first, then the label is mirrored onto GitHub as decoration-only status; the plan exclusion is the single dedup mechanism. Payload is synthesized in poller shape, so prompts/claim-swap/anomaly detector work unchanged; throttle/burst layers don't apply. Human gates and PR-anchored triggers stay poller-delivered. Authored via the **Delivery** selector on label-edge dialogs (Flow Editor) and — on an existing listener — the shared `TriggerForm` (Flow-Editor Inputs-row edit + Agent-Chat trigger editor, #1189, gated to label listeners, hidden for human gates); `transport` round-trips through the bundle (export/materialise/Edit-as-draft), rides on graph edges (dotted stroke), and flips the producer's Outcomes-block instruction to `aee-emit`. **Labelled PR/issue channels (#1194):** a labelled, non-human channel port may also carry `transport: 'internal'` (Delivery control on `EditChannelDialog` + the Routing → Inputs channel row) — its derived `<artifact>.labeled` listener is stamped internal by `expandGithubChannels` when **every** channel consolidating onto that `(artifact,label)` listener opted in (all-or-nothing, so a lone poller producer isn't dropped by the plan exclusion). Unlabelled channels (`*.opened` — artifact creation) and human gates stay poller-delivered. **Defaults (#1175):** the Flow-Weaver weaves every generated intra-stage label listener internal (stage-gate channels stay poller-delivered); the curated SDLC templates ship their agent→agent listeners internal; the advisory `internal-channel-candidate` info lint suggests the toggle on remaining poller-delivered agent→agent hand-offs; the anomaly detector's `wake-not-claimed` message is transport-aware (internal = durable queue, so it points at the consumer, not a lost event). Concept: `docs/internal-channels-concept.md`.
- `loop` — **re-arms on completion** (chains, not wall-clock): fires an iteration, then arms the next when it returns (`_loop_runner`, sibling of `_cron_runner`). Fresh context per iteration (defaults to `sessionPolicy: per-invocation`). **Stop contract**: `maxIterations` (**required**, positive int) → `exhausted`; `until.command` exit `0` → `done`; optional `maxTokens` → `exhausted`; the #611 runaway backstop → `paused`. Optional `verify` is a *separate* gate — one of `{command}` / `{agentId}` / `{flow:true}` / `{selfGraded:true}` — that must pass for an iteration to count; `{flow:true}` skips the inline gate and delegates to the flow's wired downstream QS chain (use when the loop starts a review pipeline — same reviewer won't check twice); empty/self-graded `verify` on a team agent is re-filled with a sibling reviewer role (`_resolve_loop_verify`), so an agent never silently grades its own work. Validated by `_validate_loop_trigger`; concept: `docs/loop-triggers-concept.md` §4. Agent-facing docs are injected via the Trigger-management block (`orchestrator/prompt-assembly.js`). A user **Stop** ends the loop as `stopped`; on any terminal outcome the terminal-outcome message carries a structured `io.aee.loop-record` payload (config + outcome), rendered in Agent Chat as a persistent, re-runnable finished-loop card with a "Start again" button (#1231).

Results post to `trigger.roomId` if set, else the agent's DM room. If no room exists yet the run is **skipped**. `[PASS]` suppresses output.

**Session policy.** With `sessionPolicy: per-invocation`, *triggered* runs start fresh (no `--resume`) and don't write the session pointer — DM continuity is untouched; the trigger prompt gets a learn-hint to extract lessons into `memory/log.md` first. Absent = `persistent` (legacy).

### Process Canvas / Flows (orchestration graph)

Agents + their triggers form an **orchestration graph**, authored in the **Flows** view (`/flows`, `Briefings.jsx`). **One wiring vocabulary everywhere** (#1009, concept §4.6): Input · Outcome · Action · Artifact · Consumer · Reviewer · Gate · Brake; the trigger prompt has exactly one user-facing name — **"Wake instruction — what the consumer is told"** — across edge dialogs, the chat-rail TriggersPanel and lint texts (retired: "Listener prompt", "Wake prompt override", bare "Prompt", "Connection", emit/listen phrasing). The graph/editor is the `ProcessGraphPanel` export in `ProcessCanvas.jsx`, driven by a `scope` prop (`'<teamId>' | 'draft:<id>' | 'import'`). The Flows left list selects scope: **Teams** (live graphs), **Drafts**, legacy **BriefingPack flows**. `/process` routes redirect to `/flows`.

**Process Canvas lives inside Flows.** The Process Canvas is not a standalone page anymore — it is embedded in the **Flows** view (`/flows`, `admin-console/src/pages/Briefings.jsx`). The old scope dropdown is gone; scope selection moved to the Flows left list, which lists **Teams** (live process graphs), **Drafts**, the read-only **Role-templates** blueprint, and the legacy **BriefingPack flows** (Orchestrator agents → `BPGraph`). A **New process** button there creates a draft. The graph/editor itself is the named export `ProcessGraphPanel` in `admin-console/src/pages/ProcessCanvas.jsx` — a controlled component driven by a `scope` prop (`'all' | '<teamId>' | 'templates' | 'draft:<id>'`) with `onNavigate` / `onDraftsChanged` callbacks. Flows tracks the selected process scope in the `?proc=` query param and BriefingPack flows in `?flow=`. The last-selected flow is persisted per user in `localStorage` under `flows.lastSelected.<username>` and restored automatically on return — stale or deleted flows fall back silently to empty selection; the transient `import` scope is never persisted. Mirrors the `agentChat.lastAgentId` pattern in Agent Chat. The `/process` and `/process/:teamId` routes now redirect to `/flows` (the latter with `?proc=<teamId>`); there is no longer a "Process Canvas" nav entry.

**Declarative ports are the single source of truth** for edges (siblings on a role/agent config, edited via `ConnectionsSection.jsx`, persisted via `PUT /api/agents/:id`): `emits: string[]` (label tokens the work sets — declarative only, the agent still sets the label at runtime; draws "agent → label → listening trigger"); `dataFlow.{dependsOn,inputs,outputs}` (live) ≡ role `dependsOn/inputs/outputs` (draft) — dependency/data-flow edges; `github: {producesPr?, producesIssue?}` (what a role opens — drives badges/ports + an "open a PR/issue" prompt block); `channels: [{artifact: 'pr'|'issue', from, label?, gate?, autoClaim?}]` on the *consumer* (which producer's PR/issue it reacts to; `gate: 'human'` = inline approval gate; labelled channels auto-derive a `claim` for their listener — set `autoClaim: false` on a port to opt out); `parentMemberId` ≡ role `parent` (cycle-guarded); `stage`.

**Functional triggers are derived from ports, not authored.** A draft derives them at materialise (`expandDataFlowSteps`, `expandGithubChannels`); a live team re-derives on every port write (`reconcileTeamDataFlow`, `reconcileTeamGithubChannels`) — regenerating `<consumer>-on-push-<upstream>` / `<consumer>-on-<artifact>-<producer>` triggers (marked `dataFlow`/`channel: true`), leaving hand-authored ones untouched. **A human-approval gate** is a label listener on a downstream step whose label is flagged `humanGate` in the bundle's `labels[]` registry (or gated by a channel's `gate: 'human'`) — the red gate node; never trips `gate-violation` since no agent emits it. Gate-ness is **configuration, not a naming convention** (#928): the old `human:*` prefix and the hardcoded `hold`/`needs:human` brakes carry no meaning of their own.

**Graph endpoint.** `GET /api/process/graph` (or `POST {processTemplate}`) → `{ level, team, nodes, edges, gates, labels, humanTouchpoints, lints }`. Edge `S→T` labelled `L` exists when `S` emits `L` and a `T` trigger listens via `labelFilter`. Raw GitHub-event triggers (no `labelFilter`) are `external: true`; gate/brake labels and `cron`/`once` self-loop `timer` edges originate from `null`. **Gate/brake classification reads config flags, never the label name** (#928): `labels[].humanGate` / `labels[].brake` from the bundle registry (a live team keeps it on the team agent, like `stages`) plus `channels[].gate: 'human'` — threaded into the builders as `{ labels }`. A `humanGate` label may not be agent-set (`gate-violation`); a `brake` label pauses the loop and *may* be agent-set. **Named human roles (#987, supersedes the #981 `@human` hub):** the generic `@human` actor is GONE — a person is never an anonymous hub, only a **named** `kind: 'human'` flow node. An optional `humans: [{ id, name, description?, stage?, emits?, consumes? }]` registry (persisted on the team agent like `stages`/`labels`, threaded into the builders as `{ humans }`, round-tripped through export/materialise/Edit-as-draft) declares them — purely declarative (no agent, no trigger; `triggers.json` stays byte-identical). A human's `emits` label is *implicitly a gate* (an agent emitting it → `gate-violation`); its `consumes` (`{label}` brake **or** plain delivery (notification when the label is set, no blocking — flag-based: `brake: true` in registry = brake, else delivery) · `{artifact:'pr'|'issue',from}` PR/issue review · `{artifact:'file',name}` output read) bind the gate/brake/delivery edges to that named node (first match in `humans[]` order wins; two emitters draw both edges), suppressing `producer-unconsumed`/`unconsumed-output`. A gate/brake/delivery with **no** human role wired stays UNBOUND — its edge endpoint is `null` (the renderer drops it, no hub box) and it raises an advisory `info` lint (`unbound-gate`/`unbound-brake`/`unbound-delivery`); it still lists as an unassigned `humanTouchpoint`. Bound touchpoints carry `role: <humanId>`. ### Webhook Server (`http` triggers)

Second HTTP server on `HOOK_PORT` (default `4003`). External systems trigger with:

```
POST /hooks/:agentId/:hookId
X-Hook-Secret: <trigger.secret>
```

Path must match an existing agent + an `http` trigger with matching `id`. The event is enqueued in `pending-triggers.json` (drained every 5s). **Security:** the secret is validated against `X-Hook-Secret`; secretless triggers are rejected 401 (no global "open" mode). The POST body is ignored — the trigger's `prompt` is what Claude receives.

*Known limitation:* the queue only protects against the **Maintenance Mode flag**. An event delivered while the container/webhook server is genuinely down (crash, redeploy) is **not auto-retried** — but the scheduler writes durable `in-flight-triggers.json` markers before each execution; orphaned markers at next startup trigger a "⚠️ Trigger possibly lost" DM (the human decides). Prefer `github-event` over `http` for anything that must not drop during downtime.

### Maintenance Mode and triggers

While platform-wide Maintenance Mode is active, each scheduler checks `GET /internal/maintenance-mode` before firing: `cron`/`once` inside the window don't fire; `http`/`github-event` keep queuing but stay undrained until maintenance ends; for `cron`, exactly **one** catch-up run executes after the window (never a backlog flood); `once` self-heals on the next 60s tick, `github-event` on poller restart.

### GitHub poller (`github-event` triggers)

`orchestrator/github-poller.js` polls the GitHub Events API every 30s for every repo in some env with a `githubTokenId` — for local stacks with no public ingress (polling replaces webhooks).

- **Repo discovery**: walks all envs, dedupes, picks one token per repo (first env wins); tokenless repos skipped.
- **Bandwidth**: page-1 uses `If-None-Match`; 304s cost no rate budget (~120 conditional GETs/h/repo). **Pagination**: reads further pages on a >100-event burst until an already-seen id / partial page / `MAX_PAGES`, so bursts don't drop events.
- **Cursor**: a per-repo sliding **seen-id set** (`state.seen[]`, `state.json`), not a `created_at` high-water-mark — an event is fresh iff its id is unseen. First poll only baselines. Fan-out oldest-first.
- **History horizon**: each subscriber gated by `effectiveHorizon = activatedAt ?? createdAt ?? triggers.json mtime` + 5-min grace, so a `triggers.json` rewrite doesn't shove it to "now". Derived triggers preserve prior same-id `activatedAt` (`stampDerivedActivation`).
- **Fan-out**: matched events → `pending-triggers.json` (drained every 5s), appended as a fenced JSON block. Event keys `<lowercase_type_without_event>.<action>` (e.g. `pull_request.opened`); bare `push`. The Events API omits some actions (no `pull_request.synchronize`).
- **Identity**: agents share one PAT (same actor for everyone). `gh-as-agent` stamps human-readable attribution (`commit` → author email `<agentId>@agents.local`; `stamp <file>` → `<!-- agent: <id> -->`) but this is **vestigial for delivery** — the poller doesn't read origin.
- **Resilience** (#1572): a hard wall-clock deadline (`AEE_GITHUB_REQUEST_DEADLINE_MS`, default 30 s, above the 15 s socket-inactivity timer so the more specific message wins) settles every request regardless of which phase stalls; a stall watchdog force-opens the re-entrancy guard after 5 minutes with no progress and logs a warning, so a future stuck await (e.g. mid-body socket kill) self-heals in seconds rather than requiring an orchestrator restart. Ops verification: if the poller goes silent, `state.json` mtime stops advancing — a stale mtime past 5 min with the orchestrator alive means the watchdog should have already triggered.

**Loop protection — frequency only, no source filtering.** A trigger fires on **any** matching event, including self-caused. One frequency backstop: the **conversation throttle** (`_checkAndIncThrottle`) — per `(agent, conversationKey)` sliding window, default 5 events/h (`conversationKey` groups by `pr:42`/`issue:99`/`push:refs/heads/x`). First over-threshold drop enqueues a `kind: "throttle-warning"` (plain DM), then drops silently until reset. Event-type matching, `labelFilter`, horizon are content/recency routing, not source filters. **Burst-cap digest** (`_fanOutBatch`, `planBurstHandoffs`): a group exceeding `BURST_CAP` (default 3) in one poll collapses into a single **lossless** `kind: "github-digest"` entry (plain DM) — the poll-scoped sibling of the hour-scoped throttle.

### BP-event router

Central ingestion endpoint any signaler (today ACE `bp-transition.py`) calls to announce a Briefing Pack change; the orchestrator owns routing. **Endpoint:** `POST /internal/bp-events` (port 4002, internal-only, no auth).

```json
{ "source": "<id>", "events": [ { "type": "bp:revised|bp:completed|bp:input-changed", "bp": "<12-char hex>", "details": {} } ] }
```

**Routing** (`routeBpEvents` + `bp-event-router.js`): build a reverse index `bpId → {stubId, parentOrchestratorId}`; group by hosting orchestrator (unknown BP → `unknown-bp`); force-pull the briefings clone, build the dependency graph via `loadBriefingsGraphFromExplorer()` (bp-explorer's `/api/briefings`); compute affected BPs (**`depends-on` dependents** + **input-artifact dependents** matched output→input path); apply each agent's `bp-trigger-policy`, `enableAgent` (idempotent), append a `bp-event-batch` entry to `pending-triggers.json` (a `kind`-tagged queue entry handled inline by `executeBpEvent`, not a `triggers.json` type). Dedup on `(type, bp)`; best-effort (per-target failures surface in `routed[].error`/`skipped[]`).

**Situation classification** tags each entry from the affected BP's status — each requires an explicit closing question so the chat shows the agent waiting for input:
- `kickoff` — BP `ready`, all `depends-on` `completed`/`reviewed`. Agent posts a 2–3-sentence mission summary + approach, asks for greenlight. No claim/LoopScript/commit before user OK.
- `cascade-stale` — BP already `completed`/`reviewed`/`stale`, possibly invalidated. Agent posts a summary, asks whether to `/confirm-valid` or `/revise`.
- `other` — defensive fallback → cascade-stale prompt.

**`bp-trigger-policy`** (optional, `config.json`): `mode` = `off` / `notify-only` / `notify-on-activate` (default) — `off` ignores; `notify-only` enqueues only when already running; `notify-on-activate` materializes stubs + respawns disabled agents first. `respect-manual-disable` (default `false`) — when `true`, skip activation for a manually-disabled agent.

### BP-instance hand-off (manual)

Every bp-instance chat has a hand-off action to activate downstream agents at end-of-session. Because each agent has its own workspace + repo clones, **git is the only durable bridge** — the dialog enforces this. Opening it fetches candidates (briefings graph) + per-repo git-status; submit is disabled while any repo is dirty/unpushed unless the user opts into an override (checkbox + reason quoted into every target's note). ### Admin Console authentication

The console is gated by a login screen; every `/api/*` data endpoint requires a valid session cookie (`admin-console/api/auth.js` mounts `auth.gate` over `/api`). A single env credential pair (`ADMIN_USERNAME`/`ADMIN_PASSWORD`, default `admin`/`admin`) is checked by `verifyCredentials()` — the **only** seam an SSO/OIDC integration replaces. HMAC-signed HttpOnly cookie (`aee_session`); static assets + SPA fallback stay open. **IAP SSO bridge (hosted GKE stack):** when `IAP_AUDIENCE` is set, a session-less request may instead authenticate via its Google-IAP-signed JWT (`x-goog-iap-jwt-assertion` — ES256-verified against Google's JWKS and audience-pinned in `admin-console/api/iap-auth.js`; the spoofable plain e-mail header is never trusted); a normal session is issued for the JWT's `email` **only when it matches a registered user-store subject or `ADMIN_USERNAME`** (#1415) — a registered user never sees the login form behind IAP; an unregistered IAP identity falls through to the normal login form instead of getting a silent empty-scope session. The registration lookup fails closed (unreadable users index → login form; env-admin password login, verified locally in the console, is the break-glass). Unset (compose/kind) → bridge inert, password login only.

**Per-user local passwords (interim).** Teams-page users can get a local scrypt password (never returned). Login checks the user store first (`POST /internal/admin/users/verify`), then falls back to the env admin (best-effort — no lock-out if the orchestrator is down). A per-user session's `sub` is the user's `subject`, so audit names the person.

### GitHub poller event-transparency log

Separate from the audit trail: answers "what did the poller see and what happened to it". Every **fresh** event (survived seen-id dedup) is recorded — delivered, dropped by a protection layer, folded into a digest, or matched no subscriber. Purely observational. **Writer** `orchestrator/github-event-log.js` (from `_fanOutBatch`): `ts, eventId, repo, event, actor, createdAt, label`, `ref` (#1833 — the git ref a `push`/`create`/`delete` carries, `payload.ref`; `null` otherwise), `workItem` (#1827 — the PR/issue the event happened on: `{kind: 'pr'|'issue', number, title, url}`, extracted null-safe from the enriched `payload.pull_request`/`payload.issue`; `null` for events with no work item, e.g. `push`; #1833 adds `closesIssues: [n]` on a PR work item — the issue(s) it resolves, parsed from the enriched PR body + head branch, omitted when none) + one `outcomes[]` entry per subscriber whose event-type filter matched (`{agentId, triggerId, status: delivered|dropped|digest, reason?, wakeLabel?}`); `wakeLabel` (#1846) is the label that satisfied the subscriber's `labelFilter` — set on outcomes that survived both the history-horizon and label-filter gates; `null` for any-label listeners (no `labelFilter`); absent on label-filter-dropped and history-horizon-dropped outcomes, and on rows written before #1846; `outcomes.length === 0` → `noMatchingTrigger: true`. **PR enrichment (#1833 item 2):** every `pull_request*` event is enriched with title/`html_url`/`closesIssues` before it is logged — regardless of trigger outcome (delivered / throttled / digested / no-subscriber) — via `_enrichPullRequestPayload`, cached per event id in the batch's `enrichedPayloads` Map so a PR is fetched at most once. JSONL at `/workspace/github-event-log/`, best-effort, 7-day retention. **Reader** → `GET /api/github-events` (merges day files newest-first, cap 5000). **UI**: the **GitHub Event Log** page (`/github-events`) — the Processed-events table columns are **Time · Repository · Work item · Title · Event · Actor · Outcomes** (Repository restored to an early, plainly-visible short-name column in #1833 — full `owner/name` on hover; a work-item-less push/create/delete row appends its branch to the Event cell; a PR work item trails a linked `→ closes #<issue>`).

### Direct Messages & Session Log

Each agent runs:

```
claude [--resume <sessionId>] --print \
  --output-format stream-json --verbose --permission-mode acceptEdits
```

The user prompt is written to `claude` on **stdin** (via a daemon writer thread), not passed as an argv argument — so a message that *begins* with an option-like character (`-`, en-dash `–`, German quote `„`, a `--help`-style token) is never mis-parsed by the CLI as an unknown flag (#1727); this is why the invocation uses the bare boolean `--print` rather than `-p <prompt>`. NDJSON stdout is parsed and written with wrapper events (`message.received`, `claude.invoke`, `message.posted`, `error`, `trigger.fired`) to `/workspace/agents/<agentId>/sessions/<roomId>.jsonl` (schema: `docs/agent-chat-plan.md` §4.1). Every entry carries a `correlationId` (Matrix `event_id`, or `trigger:<id>:<ts>`) tying log rows to chat bubbles.

**Per-room session pinning.** After each successful run the runner writes `session_id` to `<roomId>.current.json`; the next message in that room uses `--resume` (on failure it clears the pointer and retries once). `GET`/`DELETE /api/agents/:agentId/session/:roomId/current` read/drop it; the chat header toolbar shows *Save & Learn* directly, with *Reset Session* and *Clear History* under a `…` overflow menu (#1810). Snapshots live under `~/.claude/projects/<encoded-cwd>/` (persisted via the `claude-home` volume so `--resume` survives restarts).

**Parent-ticket binding (#1383).** A chat room can be bound to a parent GitHub issue for traceability (issue ⇄ conversation). The binding is **room-scoped** (persists across *Reset Session* — it is a separate `<roomId>.ticket.json`, not the session pointer). `GET`/`PUT`/`DELETE /api/agents/:id/session/:roomId/ticket` read/bind/unbind it; the console proxies the GitHub work to the orchestrator (`POST`/`GET`/`DELETE /internal/agents/:id/ticket`), which creates a new issue (`gh api`) or resolves an existing one (issue number or URL) with the env PAT and materialises `ticket.json` at the agent workspace root so a running agent reads it on its next invocation. Agents register child issues on the parent via `POST /internal/agents/:id/ticket/children`. Each bind/unbind appends a `ticket.bound`/`ticket.unbound` event to `<roomId>.jsonl`. Pure parsing/shapes in `orchestrator/ticket-store.js` (unit-tested). The backend endpoints remain; the Agent-Chat UI surfaces (toolbar chip, bind dialog, Sessions-panel banner, transcript rows, and the `ticket-view.js` display helpers) were removed in #1607.

**DM heuristic** (`agent-entrypoint.py`): act iff `getJoinedRoomMembers(roomId)` is exactly two (this agent + one other) AND the sender isn't this agent (cached 30s).

Reads capped at 512 KB; binary files (NUL in first 8 KB) flagged; raster images (PNG/JPEG/GIF/WebP by magic bytes, SVG excluded) rendered inline via `/image` (no cap). **Reference a workspace file in the composer (#1699):** a hover-revealed per-file `@` (Reference in chat) button splices `@<workspace-relative-path>` into the selected agent's draft, reusing `MessageInput.insertRefs` (the same caret-aware `@<ref>` path an upload/attach produces, so the agent resolves it from its cwd without a re-upload). Files only (never directories) and only for real workspace keys — a `/context` host-mount key (leading slash, not agent-resolvable) is hidden. Cross-panel wiring: `WorkspaceBrowser` (RightRail) → `AgentChat` lifts an `{ref, ts}` request-object → `ChatPanel`/`MessageInput` (siblings; same request-object pattern as `railTabRequest`/`resumeRequest`); the consumer effect seeds `lastInsertRefTs` from the incoming `ts` so a request left over on an agent switch never re-fires on the freshly-mounted composer.

**Context-folder browsing (#1286, multiple folders #1290).** An agent with host-folder mount(s) (#1283) grows one **virtual read-only root per folder** in the same tree, keyed by its in-container target — `/context` for a single legacy folder, `/context/<slug>` for each folder in a multi-folder set. The leading slash, which a real relative workspace path can never have, means a workspace folder literally named `context` cannot collide. It is not served from this container: the host folder exists only inside the *agent's* container, so `GET /api/agents/:id/context/{status,tree,file,image,download}` proxies `/internal/agents/:id/context/{tree,file,download}`, which runs a one-shot `list`/capped-`read` via `orchestrator/container-exec.js` (libpod exec create → start → docker-frame demux) inside that container. Pure rules — request-side path guard, the browse program, output parsing, the error-code → HTTP table — live in `orchestrator/context-browse.js`; containment is enforced **twice**: no `..`/absolute path in, and realpath containment under `/context` in the container (an escaping symlink is listed as `other` and never readable). Requires the agent to be running (`409` otherwise). Frontend source routing is the pure `workspace-source.js` (`isContextKey`/`workspaceUrl`/`withContextRoot`).

**Context-folder writing (read-write mounts).** A **read-write** mount (`readWrite: true`) also gets upload / delete / drag-move in the same tree; a **read-only** mount stays browse-only (its rows offer no write action). Symmetric to browsing: the mutation runs inside the agent's container and the console is a proxy — `DELETE /api/agents/:id/context/file`, `POST .../context/move`, `POST .../context/upload` proxy `/internal/agents/:id/context/{file,move,upload}`. Delete/move run a one-shot Python `WRITE_PROGRAM` (realpath containment under `/context`, sibling of the browse program) via `orchestrator/context-write.js`; upload streams the raw bytes (no base64) into the container through the libpod **archive** endpoint (`putArchiveToContainer` in `container-exec.js`) after a `prepare-upload` exec validates the target dir + de-duplicates the name, packaged by the dependency-free ustar builder `orchestrator/tar-single.js`. Guarded **three** ways: per-mount `readWrite` gate in the orchestrator route (403 on a read-only mount), realpath containment in-container, and the **kernel EROFS backstop** (a read-only bind mount rejects every write regardless). A move is a rename within **one** mount — cross-folder and workspace↔context drags are refused (`sameWritableSource`); the mount **root** itself is never a drag source or deletable (you delete files *in* it, not the mount point). Frontend gating is mount-aware in `workspace-source.js` (`isReadOnlyKey(key, status)`, `mountForKey`, `writeApiBase`/`apiRelOf`), threaded through `WorkspaceBrowser.jsx` from the `/context/status` payload.

**Markdown safety.** Sanitized with `rehype-sanitize` (GFM `defaultSchema` + `style`/`data-*` for `rehype-pretty-code`), run *after* pretty-code so highlighting survives. Both Shiki themes shipped; active theme via CSS keyed off `<html data-theme>`.

**Meeting Note-Taker — persistent transcription overlay (#1296).** Quick voice dictation (the `MessageInput` mic tap → `useVoiceRecorder` → draft insertion) is page-scoped and unchanged. **Meeting mode** is a separate, explicitly-chosen action: the mic becomes a split control (chevron → "Record meeting for &lt;agent&gt;") that starts an **app-level** transcription session which survives all client-side navigation — the mic is never released when the composer unmounts. The engine is `TranscriptionSessionProvider` (`src/context/TranscriptionSessionContext.jsx`, mounted in `src/index.jsx` inside `AuthProvider`): it owns the `MediaStream`, records in fixed **120 s segments** (each a standalone webm/opus blob transcribed via the existing single-shot `POST /api/transcribe`, up to 2 retries → a `[transcription gap]` marker on failure, never aborting the session), and on **Stop** assembles the ordered segment texts into one message auto-sent to the originating agent's DM room (`POST /api/matrix/agents/:id/dm` → `.../rooms/:roomId/messages`). A `TranscriptionOverlay` (portaled to `document.body`, rendered once in `Shell.jsx`) shows the live card (recording/paused/transcribing, elapsed, agent name → chat, Pause/Resume · Stop · Cancel) on every page. Recovery: after each transcribed segment the segment *texts* (never audio) are persisted to `localStorage['transcription.recovery']`; a `beforeunload` guard + an on-mount recovery banner (Deliver partial / Discard) cover a hard reload/crash. One active session per tab. The deterministic core (state machine, segment assembly, transcript/message formatting, recovery-record shape) is the pure, `node --test`-covered `src/context/transcription-session.js` (per the #651 pure-module convention); the provider is the thin browser adapter. Backend: the only server change is `admin-console/api/transcribe.js`'s STT timeout, now env-configurable via `STT_TIMEOUT_MS` (default **60 s**, was a hard-coded 15 s — a 120 s segment can exceed it on CPU).

**Helper Chat — app-level Help panel (#1735).** A **Help** button (`HelpCircle`) in the Shell header right-cluster toggles a non-blocking slide-in assistant available on **every** route. The engine is `HelperChatProvider` (`src/context/HelperChatContext.jsx`, mounted in `src/index.jsx` alongside `TranscriptionSessionProvider`) so the panel **and its conversation survive all client-side navigation**; consumers reach it through the `useHelperChat()` hook. `HelperChatPanel` (`src/components/HelperChatPanel.jsx`) is rendered once in `Shell.jsx` next to `TranscriptionOverlay` — a right-edge `position:fixed` panel with **no backdrop**, off-screen (`translateX(100%)` + `pointer-events:none`) when closed. On submit it POSTs the newest **≤20** turns plus the current route + friendly route label to `POST /api/helper/chat` (the #1734 endpoint) and streams the `{type:'delta'}`→`{type:'done'}` NDJSON into a streaming assistant bubble (the shared animated `ThinkingDots` indicator while streaming, matching Agent Chat — #1779). The deterministic core — message-list transitions, request shaping (trim to `MAX_TURNS`=20), NDJSON line framing (`splitNdjson`) and the static `SUGGESTED_PROMPTS` empty-state chips — is the pure, `node --test`-covered `src/context/helper-chat-model.js` (per the `transcription-session.js`/#651 convention); the provider is the thin browser adapter owning the `fetch` + stream reader. Route grounding uses the `BREADCRUMBS` map + `breadcrumbFor`, extracted from `Shell.jsx` into shared `src/components/breadcrumbs.js` (single source of truth for both the breadcrumb bar and the panel's route label). Markdown reuses Agent Chat's `SafeMarkdown` + `ensureAgentChatMdCss` (now exported from `pages/agent-chat/Message.jsx`) for the same sanitised-markdown/Shiki pipeline in both themes; the animated loading indicator reuses the exported `ThinkingDots` (its `@keyframes dotPulse` self-injected via `ensureThinkingDotsCss`, with a `prefers-reduced-motion` fallback) and the composer reuses the shared `useVoiceRecorder` hook for a quick-dictation mic (record → `POST /api/transcribe` → appended to the draft), so both the loading indicator and the mic reach visual/functional parity with Agent Chat without a parallel implementation (#1779). A **[Chat] [Tour]** tab bar (#1737) switches the panel between the chat face and a guided **tour** face (`HelperChatTour`, `src/components/HelperChatTour.jsx`): a chapter list + per-chapter step carousel whose data comes from `GET /api/helper/tour-manifest` (served via a guarded loader that degrades to `{chapters:[]}` until the #1736 manifest data lands) and whose progress persists under the `helper-chat.tour-progress` localStorage key; `useHelperChat().openTour()` opens the panel straight into tour mode — used by the `/getting-started` **Take the Tour** button and a CTA in the chat empty state. The tour view's deterministic core (chapter ordering by `order`, the progress shape, resume/step math) is the pure, `node --test`-covered `src/context/tour-view.js`.

## Skills

Skills live in the skill-pool volume (`agent-studio_claude-workspace`) under `skills/<name>/SKILL.md`, granted per **agent construct** (team `skills[]` / standalone `skills[]` / member `skillsOverride`) via the Agents page, the wizard's Knowledge step, or the Knowledge page. Environments have **no** skill picker. **Agents page create form**: the SkillPicker for `agent`/`orchestrator` roles pools `source==='pool'` only (global pool — no team context at create); team-tier skills appear in the edit form once the agent belongs to a team. `role==='team'` create form correctly shows the team-inheritance framing. Intended domain: **Mainframe Migration** (COBOL, JCL, DB2, IMS/VSAM).

### Two-tier skill pool

Resolved **team-first then global** at seeding. **Global**: `/template-workspace/skills/` (orchestrator RO) = `/pool/skills/` (admin-console RW), System-Admin-managed, all teams. **Team**: `/workspace/teams/<teamId>/skills/` (RW), Team-Admin-managed, that team only. `orchestrator/skill-source.js` (`makeSkillSourceResolver`) copies each grant name from the team's pool when present, else global. `/api/skills` tags `source` = `pool`/`team`/`agent`; `POST /api/skills/promote-to-global` lifts a team skill into the global pool.

### Custom slash commands (#1796)

A granted skill may **carry Claude Code slash commands**: a `commands/*.md`
subdirectory in the skill dir. Wherever the skill is seeded or (de)activated, the
pure `orchestrator/skill-commands.js` projects those command files into the
agent workspace's `.claude/commands/<skill-slug>/<name>.md` (invoked as
`/<skill>:<name>`) as an **additive file sync, no respawn** — same path as skill
files (`seedAgentWorkspace` / `_syncSkillIntoWorkspace`, mirrored into the
isolated volume). The optional `description` front-matter is parsed and written
to `/workspace/agents/<id>/.agent-studio/seeded-commands.json`, exposed via
`GET /api/agents/:id/commands` for the #1797 autocomplete. There is **no** new
grant type and no ad-hoc authoring — commands ride the team-scoped skill grant.
On the **chat path only** (`agent-entrypoint.py`), a provisioned `/command`
expands natively in `claude --print` (verified — unlike the interactive-only
`AskUserQuestion`, #1712), and an **unknown** `/token` is neutralised (a leading
space is prepended) so it is answered as plain text instead of the CLI's
`Unknown command` short-circuit (AC2); a `slash.command` session-log event
records recognised/unknown. Full reference + headless findings:
`docs/slash-commands.md`.

### Knowledge digest (guaranteed context injection)

Part of the memory/knowledge unification (`docs/memory-knowledge-unification-concept.md`). Every KB-provisioned agent carries a generated **`knowledge-digest.md`** at its workspace root, `@`-imported by the seeded CLAUDE.md — so team conventions, converged (learned ≥2×) and recent lessons are **guaranteed in context at session start**; `knowledge search` is the long-tail complement. Deterministic (no LLM), ~3k-token budget, built by one pure module kept byte-identical on two sides: `orchestrator/knowledge-digest.js` ↔ `build_knowledge_digest()` in `agent-entrypoint.py` (golden fixture `knowledge-digest.fixture.json`; change both in one commit). Runtime rebuilds pre-invocation; `refreshKnowledgeClone` fans out post-KB-change. The `@`-import is gated (`knowledgeDigestRef`) on a provisioned checkout, so autonomy-0/KB-less agents see nothing.

**Semantic rerouting.** `agentKnowledgeDigestRef(id, env)` (autonomy ≥ 1 + provisioned checkout ≡ `_memory_model_unified()`) flips the digest import, swaps the Memory System section to the unified variant (episodic `context.md`/`log.md`/`users.md`; `facts.md`/`entities.md` read-only legacy — new semantic knowledge goes to `knowledge add`), and selects the unified memory hint. The legacy five-file model is the autonomy-0/KB-less/blueprint fallback. `users.md` is personal data — never shared, never migrated.

**Migration.** One-shot per unified agent (`migrateAgentMemoryToKb`, `orchestrator/memory-migration.js`): legacy `facts.md`/`entities.md` → KB entries in a dedicated shard `<kind>/shards/<agentId>.migrated.jsonl` (never the agent's own — avoids a two-writer race), committed+pushed; only after the push are files archived to `memory/_archive/`. **"in digest" indicator**: `buildKnowledgeDigest` returns `includedIds`; `GET /internal/teams/:teamId/knowledge/digest-status`; the Knowledge tab renders a green `digest` badge.

## MCP Servers (operator notes)

Reference servers ship under `mcp-servers/<id>/`; `make seed-mcp-servers` (chained from `make seed-pool`) syncs them to `/template-workspace/mcp-servers/`. Add a backend by: (1) drop a single-file MCP (stdio or http) under `mcp-servers/<id>/`, (2) `make seed-mcp-servers`, (3) register via the **MCP Servers** admin page + bind a credential + attach to environments. The `wiki/` reference server is tiny and dependency-free — clone it as a starting point.
